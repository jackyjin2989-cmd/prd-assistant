# 边界扫描清单

在内部按本次改动类型查漏，不将清单变成 PRD 目录。只处理直接影响当前产品行为或业务结果的项；问题提示不是要求产品具备每个分支，也不是允许自行补规则。

不设计锁、事务、重试算法或性能实现；重复提交、失效状态、等待或失败等若有本次产品可见后果，仍需扫描条件、反馈和用户下一步。

## 状态与枚举改动

- 旧状态或旧枚举在已有数据的列表、详情、筛选、报表和导出中如何呈现？
- 新状态从何而来、到何而去、谁能触发？哪些分支实际存在？
- 其他模块、消息或通知是否引用同一状态或旧文案，需要同步调整哪些位置？

## 字段改动

- 新增字段在存量数据无值时如何展示，是否回填？新增必填是否影响旧数据再编辑？
- 列表、详情、编辑、筛选和导出的归属是否清楚，是否确实都要改？
- 删除字段后哪些页面展示要移除，存量值保留、清除或另行处理的规则是否明确？
- 本次涉及的空值、真实 0、超长、极值、精度和舍入是否明确？“不展示 0”不能自动解释成“无值显示破折号”。
- 取值来源是否有材料依据？未知来源、阈值或格式不能靠惯例补齐。

## 流程改动

- 已确认存在的通过、驳回、取消或超时分支，分别停在哪个状态、用户看到什么？
- 关闭弹窗或中途放弃后，已填内容和单据状态怎么处理？
- 生效时在途单据采用新规则还是旧规则？日期边界涉及自然日、工作日或时区时是否明确？
- 空数据、查询无结果等本次相关场景如何展示？
- 上下游引用同一数据时，展示、操作和结果是否一致，联动方向是否清楚？
- 用户重复点击、再次提交或操作已失效状态时，是否有已确认的可见结果？等待或失败后如何继续？只查命中项，不自行加入限时、重试次数或恢复策略。

## 权限改动

- 已确认哪些角色可见入口、可执行操作？查看与操作是否需要区分？
- 无权限时隐藏、置灰还是提示？直接访问时如何反馈？不能把这些备选当默认答案。
- 新权限是否影响存量账号，既有分配如何处理？

权限写法及矩阵例外见 [写法指南](写法指南.md)。不得凭经验分配角色权限；核心权限缺口按入口规则处理。

## 展示与多端一致性

- 同一数据在涉及的端、导出和消息中的名称及口径是否一致？
- 已确认的格式、单位、精度和时区是否沿用正确？
- 文案或 UI 删除是否覆盖本次要求的位置？不要把“移除分割线”“不显示某行”误当技术细节删掉。
- 只有同一句改动同步到多端时，不因端数量直接判为复杂业务。

## 使用规则

按 [SKILL.md 的“未知与定稿”](../SKILL.md#未知与定稿) 处理：核心未知和核心冲突阻止定稿，需要用户决定的非核心问题也及时追问；符合入口记忆条件时同步记录，只有用户明确暂缓后才在 PRD 标注，无关项不输出。用户已委托自主决定的细节按授权处理。只审校时报告问题，不修改源文；局部修改不能因扫描命中其他问题而扩大写入范围。扫描过程与“已检查无影响”自证不进入 PRD。
