# PRD 写法指南

先按 [SKILL.md](../SKILL.md) 确定模式、交付物与 A/B/C 复杂度。事实和有效硬约束、明确交付要求优先于默认精简。模板是裁剪工具，不是必填目录；完整输入输出见 [示例.md](示例.md)。

## 通用写法

优先回答：改什么；何时、何地、由谁操作；展示或业务结果是什么；还有哪些未定。只写本次涉及的字段、状态和分支，不为填满格式补信息。

- 一条规则在一处完整定义，其他位置引用；共同规则不跨端复制。
- 背景有助于理解时简述，不言自明时省略。
- 未知与冲突按入口规则处理：核心事项阻止定稿，非核心事项就地标注；不输出整套内部事实分类。
- 用户可见异常写条件、反馈和下一步，不推导内部恢复机制。
- 动笔前按 [边界扫描清单](边界扫描清单.md) 查本次命中项；扫描提示不是预设答案。

## 规则未约定

| 已确认情形 | 写法 |
|---|---|
| 本产品不定义，且不影响本次行为或边界 | 不新增规则；仅在授权修改范围内删除无用说明 |
| 由别处的有效规则决定，来源与适用范围已确认 | 保留准确引用，不重复抄取值，也不删除必要来源 |
| 本产品必须定义但尚未决定，或来源不明 | 按核心影响追问或就地待确认，不能伪装成“以某系统为准” |

例如，输入明确“标签长度由工作区设置中的‘标签长度上限’控制，本页沿用”时，可引用该字段。只有“长度以实际为准”时，不能推定存在这一设置或任填阈值。

## 表格准入

适合对照的字段、校验、状态或权限规则用表格；简单规则直接写一句话。每行至少承载一项影响理解或实现的真实信息，列按问题选，不要求“取值来源”和“展示逻辑”同时有值。

- 字段表可选名称、控件、取值、默认值、必填、展示或校验；没有的信息不为填列而猜测。
- 条件与结果两列就能表达一条校验，不必添加无关来源列。日期、单位等有真实格式规则时也可单列。
- 全无信息的列、重复行可以删；重要但未知的条件标待确认，不以“空表格”为由抹掉。
- 仅有无附加规则的名称清单可合成一句。例如已确认“页首展示素材名称、类型、更新时间”时，直接照写，不另造公式、取值来源或格式。

## 存量数据与权限

存量只写受影响的对象、生效边界、处理后的业务表现和必要取值规则。兼容展示、一次性初始化、新老划断是常见方式，不是封闭枚举；保留、清除或纠错等其他已确认方式可以直接描述。不同字段可采用不同方式，不能只说“存量保持不变”来回避实际影响，也不自动补迁移执行 SOP。

权限写本次必需且已确认的角色、权限点、入口、操作范围和无权限表现，包括有需要时的直接访问反馈。不擅自为角色分配权限。隐藏、置灰和提示是不同选择，缺少输入不能任取其一；关键权限未知按入口规则追问。矩阵等格式按下表处理。

## 按需内容（唯一例外表）

本表统一定义默认精简的例外，适用于 A/B/C 和全文整理；局部修改不因此扩大范围。没有触发条件就不补章节，已有内容也不因命中某个标题而自动删除。

| 内容 | 何时纳入、写到什么程度 |
|---|---|
| 验收标准、测试用例 | 用户明确要求时，按本次范围简短补充，不默认复制整套规则 |
| 范围排除 | 用户明确要求，或不写会实质误解本次交付／生效边界时，用最短表达消除歧义；不列无关的“不做”清单 |
| 版本信息、正式历史、变更日志、方案比较 | 用户明确要求或已有批准记录确有持续维护价值时保留；与现行正文分区，标清历史或比较身份，不能当作当前规则 |
| 需求／规则／验收编号、追踪矩阵 | 用户明确要求，或既有有效引用关系需要保留时；只保留必要标识，不默认创建矩阵 |
| 角色权限矩阵 | 用户明确要求时按已确认权限填写，未知不补造；不替代必要的权限行为说明 |
| 名词解释 | 专有名词影响理解时解释相关词，不编写通用词典 |
| 流程图 | 用户明确要求，或多角色、多状态关系难以用短文说清时；优先用 Mermaid，不以编号步骤冒充流程图 |
| 图片 | 用户要求，或能明显减少本次页面歧义时；选图与嵌入见图片指南 |
| 原型 | 仅按入口“原型分流”触发，写 PRD 不顺带制作 |
| 多语言 | 用户明确要求或已有适用产品机制要求时；未给译文不冒充已批准文案 |
| 校验汇总 | 相关校验较多且分散、汇总能减少理解成本时；避免重复定义 |
| 非功能要求 | 用户明确要求或构成本次产品行为的必要约束时；不自行设阈值 |
| 成功判定 | 用户明确要求，或需求本身需要衡量增长、效率等目标时；写指标含义、统计对象／计算口径及已知基线、目标、周期，缺项按统一待确认规则处理，不自动生成数字或埋点方案 |
| 技术、发布、迁移、运营、风险、里程碑、FAQ 等 | 用户明确要求或属于已确认的必要产品约束时，只写相关部分；不因模板有此项扩成技术或项目管理文档 |

范围示例：输入已确认本次仅改 PC，但评审仍预期 H5 同步，可写“本次仅调整 PC 页面”。若相邻导出能力无人要求、也无合理交付预期，不为凑边界写“不改导出”。已确认的“禁止导出”则是产品限制，不是可删除的范围赘述。

## A 微调型

沿用既有流程的局部改动，即使多个端同步也可为 A。默认只需“改动点”，必要时加一句背景。通常半页以内，必要信息优先于长度；例外按上表，不另设绝对禁令。

每条写清本次涉及的位置、条件、增改删内容、规则和结果。已确认沿用的校验或存量行为可以准确引用，不能把没给的信息假定为沿用。负向 UI 改动和计算限制原样保留也可以。

## B 模块级

边界明确、规则可在一个模块或局部流程内闭环。按需组织：

1. 背景与本次范围；跨多个页面且容易混淆时可用范围表。
2. 按页面或操作路径写入口、字段、操作、结果、关键状态和可见异常。
3. 相关业务规则、受影响存量和待确认项；内容少时并入对应段落。

状态表只写实际存在的状态、操作和流转条件；不因为表格有“取消／超时”列就发明分支。

## C 耦合业务型

需要统一共享对象、跨角色状态或跨模块责任时采用；端数量不是判定依据。建议先定义共同规则，再说明各角色或模块的不同操作。

- 集中定义共同对象、状态、计算口径和流转条件，必要分支不能为简短而省略。
- 分模块说明入口、可见内容、可执行动作与结果，引用共同规则。
- 写明联动方向：哪个角色或端的动作，引起哪些业务状态及其他端展示变化。
- 受影响存量和真实未定项按需落在相关段落。主流程图只按上表触发，不要求 C 必画 Mermaid。

复杂业务不是默认技术设计：接口、数据结构、同步机制等仍受按需表与当前授权限制。

## 表达与交付

按 [语言表述规范](语言表述规范.md) 精简；按 [review-checklist.md](review-checklist.md) 清理无效讨论残留。现行正文写采用后的方案，必要正式历史独立标识。图片紧邻解释，路径与复用按 [图片嵌入与截图指南](图片嵌入与截图指南.md) 处理。交付说明不混入业务规则，不以自证总结代替内容。
