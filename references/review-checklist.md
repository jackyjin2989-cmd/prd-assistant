# PRD 审校与交付清理

质量北极星：**研发读完对应章节即可动手实现，不需要再来问"这里是什么意思"。**以下检查项都服务于这一条。先判断需求类型，再检查核心产品信息是否足以评审。不要用模板章节数量衡量质量，也不要因缺少技术方案、验收标准或原型而判定 PRD 不完整。

## 一、篇幅与边界

- A 类是否半页以内、只有改动点（和必要的一句话背景）。
- 是否出现了用户未要求的验收标准、本期不做、成功判定、里程碑、FAQ、总结段（[写法指南.md](写法指南.md) "按需内容"表允许的情形除外）。
- 是否围绕本次核心功能和改动，没有无关扩写。
- 产品可见异常是否只说明触发条件、反馈和用户下一步，没有推导内部实现。

## 二、通用检查

1. 每条改动是否写清位置、条件、行为、规则和结果。
2. 角色、页面、字段、操作、状态是否只覆盖实际涉及的部分。
3. 枚举、默认值、必填、展示条件和校验文案是否明确。
4. 用户可见异常是否有明确反馈和可继续路径。
5. 存量数据是否只在受影响时说明处理规则；写了的话是否落到兼容展示 / 一次性刷数 / 新老划断之一，没有"保持不变"一句带过。
6. 对照 [边界扫描清单.md](边界扫描清单.md) 本次改动类型的小节：影响本次改动的缺口是否已写进正文或待确认项。
7. 同一规则是否只定义一次，没有跨章节重复或口径漂移。
8. 术语是否统一，语句是否直接、自然、无套话（对照 [语言表述规范.md](语言表述规范.md)）。
9. 核心分歧是否已集中追问；非关键待确认是否只是标注而没有展开讨论过程。

## 三、按类型检查

### A 微调型

- 文案改动是否给出位置和最终文案。
- 字段改动是否写清取值、默认值、必填、展示和校验。
- 是否没有版本信息、名词解释、流程图等注水内容。

### B 模块级

- 功能入口和适用角色是否明确。
- 页面、字段、操作、关键状态和业务规则是否闭环。
- 用户操作前后的可见结果是否明确。

### C 跨产品复杂业务

- 核心业务流程、共同角色和状态口径是否明确。
- 各产品端的入口、展示、操作和结果是否互相一致。
- 跨端规则是否集中定义，没有重复复制。

## 四、原型与图片（有原型交付时）

- 是否只在满足 `SKILL.md` "原型分流"条件时生成了原型。
- 截图驱动原型是否先识别界面身份、骨架、组件形态、密度和视觉令牌，未擅自改成通用模板。
- 视觉验证是否按 [prototype/visual-validation.md](prototype/visual-validation.md) 的能力判定执行或降级，结论为一句话的"通过 / 受限 / 未完成"。
- 结论非"通过"时，是否避免了"高还原""已复刻"等表述。
- 图片路径为相对路径且文件存在，无裂图和占位。

## 五、编辑残留与最终交付

解决"此地无银三百两"问题：方案已经改对，PRD 里却把讨论中淘汰过的内容又写了回来。核心原则：**从最终采用的状态重写正文，被否方案当作不存在。**对每处内容问一句：没有参与过这轮对话的读者，需要这条信息吗？

**不保留：**

- 只在聊天中讨论过、从未采纳的方案
- 用户纠正过的标题框架、语气和自证句
- 用近义改写、括号或"无 X""非 X 版""已清理"等标签保留的被否内容
- "本期不做/范围排除"——默认不写；仅用户明确要求，或不写会导致读者误解边界时一句话列出，不解释否决原因
- "XX问题已判断""XX问题已解决"等分析过程字样

**"误解边界"的判据（避免被当成万能口子）：** 只有该范围不做会让研发**实现错功能**时才算。仅是需求取舍、要不要做、以后再做，都不算。

**范围排除：违规写法 → 正向改写**

| 写坏 | 改法 |
|---|---|
| 基金对比、定投、费率优惠本期不做 | 删除整行，范围由正向的「页面范围 / 本期范围表」表达 |
| 仅展示当前费率，不做原价/优惠价对比（本期无费率优惠功能） | 展示在买入金额输入框下方，与起投金额同行 |
| 页面上不再单独展示「最多可卖出份额」行 | 可用份额即最多可卖出份额 |
| 不区分可用/软锁/硬锁，不展示「软锁份额」「硬锁份额」 | 份额明细区分持有份额、冻结份额、可用份额三行 |
| 子行之间不再加分割线 | 删除（属实现细节，不是产品口径） |
| APP 不做净值计算 / 不展示 0 或空白 / 不参与取值优先级 | 由后端计算后下发 / 无值时展示 `—` / 独立于取值优先级 |
| 只做原型上已有的模块 | 删除 |

判断法：把句子里的「不」拿掉，若剩下的是本轮要做的事，就改写成正向句；若剩下的事本轮不做，就整句删除。

**保留：**

- 安全、法律、兼容性等硬约束
- 用户明确要求的方案比较、变更日志或迁移说明
- 已发布能力确实被移除时的迁移说明

**生成规则：**

- 标题从最终正文重新生成，不出现被否方案的名称或对比框架。错误：`充值审核流程优化（不含自动审核）`；正确：`充值审核流程优化`。
- 确需写范围排除时只写"本期不涉及 X"，不写"（曾考虑但因 Y 否决）"。
- 交付说明只包含正向结果和验证状态，不复述讨论过程。

**交付前逐项检查：**

- [ ] 无"无 X""非 X 版""without X"等标签，无解释某方案为何不存在的说明
- [ ] 无删除线、草稿标记、占位文字、批注式说明和会话残留
- [ ] 无分析过程字样
- [ ] 被否方案未以任何方式重新出现
- [ ] 标题、范围和交付说明只描述最终采用方案
- [ ] 正文不含交付物清单、截图出处和原型功能说明（项目惯例要求附原型链接时除外）
- [ ] 正文不含 REQ/RULE/AC 编号和追踪矩阵
- [ ] PRD 与原型为独立文件

发现问题就修订后重查一遍；仍有实质性歧义时向用户确认。

## 六、审校输出

1. **结论**：可评审 / 补充后可评审 / 核心方案待确认。
2. **关键缺口**：只列影响核心功能的问题。
3. **重复与矛盾**：指出位置并给统一口径。

不要把默认不要求的验收、技术、发布、运营或原型内容列为缺口。
