# 图片嵌入与截图指南

本文件定义 PRD 配图的选择、路径、复用、排布和图文一致性。原型实现见 [generation.md](prototype/generation.md)，截图能力和验证状态见 [visual-validation.md](prototype/visual-validation.md)，不在此另设自动化流程。

## 何时配图

- 先识别图片身份。现状截图默认仅作 reference，不直接贴入目标 PRD；改造后的页面使用新原型截图。仅用户要求现状说明或前后对照时放入旧图，并清楚标注“现状参考”。使用项目自有或已获授权材料，图片应支持相邻需求，装饰图、重复图及不适用的旧图不纳入。
- 仅 PRD 也可以配图，但不因此默认生成原型。仅原型只交 HTML 和必要验证说明，不附加 PRD。
- 同时交付 PRD 与原型时，在已有截图能力可用、且有信息价值时嵌入静态截图。不能截图则不造图或留占位，在交付说明报告未覆盖状态及限制。
- 模糊截图只采用可辨识内容；未知文案与规则按入口处理，不能放大猜测。

## 覆盖范围与状态真实性

先按本次视觉歧义选必要页面和状态。未要求穷举时，不把正文的每个条件都变成截图任务；用户明确要求全状态则先界定覆盖集合。选入的每张图必须真实对应所说明状态，不能用默认态顶替弹窗态、空态或无权限态。

改了文案、布局或状态逻辑后，识别受影响图片并重拍；不能截图时标明验证受限及未覆盖项，移除会误导当前要求的旧配图引用，不能宣称新图已验证。已知实现错误仍需如实说明，不能藏在能力受限中。

## 业务正文与交付说明

业务正文只放解释需求的图片与必要图注。状态进入方式、截图环境限制、多图检索索引和交付物清单默认放交付说明；仅在确有复现价值时记录，不为少量图片新增索引。

进入方式必须实际支持，例如原型确有对应参数时记录 `?state=dialog`，或记录已验证的点击路径。项目已有明确附录惯例且与当前授权相符时可以沿用，但不让这些元信息混为业务规则。

## 命名与复用

- 使用稳定、可读的页面／状态名称，例如 `01-素材列表-空状态.png`；编号可选，语义和引用稳定性优先。
- 同一图片可以被同一文档、索引或其他获准范围内的文档多次引用，不要因此复制文件。
- 核对规范化后的**唯一引用路径集合**，确保每个目标存在；引用次数不需要等于文件数。
- 仅在明确获准的交付根内检查资源归属。判断未引用图片时需考虑授权范围内的共享引用；范围外未知用途不得推定为无用，不自动删除共享文件。
- 增量改动不因插删图片整体重编号。确需重命名时限于授权范围，并更新已知引用；不为连续编号破坏共享引用。

## 脱敏与路径

- 遮蔽或替换个人身份、联系方式、账号、订单标识、内部地址和其他敏感信息；密码、验证码、Cookie、令牌与登录态不入图。
- 脱敏后保留必要布局、字段类型和状态关系。
- 引用使用相对 PRD 的路径和非空替代文本，如 `![素材列表空状态](images/01-素材列表-空状态.png)`。本行仅为格式示例，真实交付需用存在的文件。
- 禁止本机绝对路径和 `file://`；正确处理空格及编码，核对大小写与扩展名。先解析规范化路径并确认实际目标位于授权交付根，再读取；根内共享资源可以引用，路径写法不能绕过访问边界。
- 没有实际图片就不保留“待补图”或虚假文件链接；真实业务未知按入口规则先追问并记入需求记忆，用户明确暂缓后才进入 PRD。

## 排布与可读性

图片靠近对应描述或小标题，不把各模块截图无差别堆在末尾。一段涉及多个状态时，图注应能区分每张图。

横排只在图片共享比较目的、缩小后仍可读、目标渲染器支持且窗口容得下时使用；不预设手机必须三四张一行或 PC 必须两张一行。高密度图优先宽图或必要局部图，窄窗口可减列或竖排。不能为了缩短文档牺牲辨读。

GitLab 横排按下节实现；其他目标须核对其 HTML 支持。目标不支持时可竖排；用户明确要求并排而目标不支持时先说明限制并协商，不能自行合成图片替代。有裁切图时说明局部范围，不把大视口裁图当作小视口响应式验证。

### GitLab 横排的唯一写法

GitLab PRD 的多图并排使用 **HTML 表格 + 像素宽度 + `<br>` 图注**。按会被清理 `style` 的渲染环境设计，不依赖 `display:flex`、`display:grid`、内联 `max-width:100%` 或百分比宽度。

以下是两张原始宽度为 494px 的独立图片示意；真实交付替换为存在的路径、图注和本次标定宽度：

```html
<table>
<tr>
<td align="center" valign="top"><img src="images/01-list.png" alt="改造后列表" width="494"><br>图 1：改造后列表</td>
<td align="center" valign="top"><img src="images/02-dialog.png" alt="改造后弹窗" width="494"><br>图 2：改造后弹窗</td>
</tr>
</table>
```

1. 采用 `<table>`、`<tr>`、`<td align="center" valign="top">`、`<br>` 与 `<img width="像素整数">` 这些兼容结构，每个单元格一张独立图片和其图注。单图也可使用只有一个单元格的表格。
2. **宽度给接近原图宽度 + 实测标定值**。先读取源图实际像素，结合目标列宽、图数、字迹及缩放效果标定，不能固定套用 180/240。既有标定记录：源图宽 494px 时，三张一行曾用 `440`，两张一行 `494`，单图 `620`；这些是特定容器的历史值，不是任意图片通用的默认值或本次实测结果，单图放大也须检查清晰度。
3. **“并排”就是多张独立图片在一行的排版，不是合成一张 PNG**；保留独立源文件、可单独查看的图片及可单独修改的图注。本流程不设合成图兜底。只有用户另行明确要求拼接图时才制作该独立交付物。
4. 不假设目标站点的全局 CSS 一定自动缩小或消除溢出。先在接近目标内容列宽的容器预检，再在有已授权预览能力的目标 GitLab 核对宽度、图注和溢出；记录视口／容器宽度、源图宽度、`width` 属性和实际渲染宽度。
5. 过密时优先减少每行图片数，或在目标页面支持的视口重新截图；不要仅为了并排改变产品布局、裁掉需求或把文字缩至不可辨读。点开原图用于查看细节，不替代正文内基本可读性。
6. 只有实际核对目标渲染后才声称 GitLab 排版已验证；仅模拟容器时说明预检范围，无法预览时说明尚未实测，不把历史标定当作本次通过。

## 图文一致性

本节是图文一致性的唯一完整定义。逐图检查它能否支持相邻描述，再回到已确认需求判断修正方向：

1. 原型错误：在授权范围修原型并重拍，不能倒改需求迁就实现。
2. 正文错误且有明确确认依据：按任务模式修正或提出建议；只审校仍不改源。
3. 来源冲突或核心信息不足：按入口规则追问并暂停定稿，不任选一个版本凑一致。

例如，已确认“无查看权限时不展示预览图”，配图却出现预览图，就不能改成“无权限也可预览”来通过检查。该图需修正；不代表所有未选入的权限组合都要补拍。

## 交付前检查

检查图片来源与授权、脱敏、稳定命名、所有唯一引用目标的存在性、就近解释与可读性，并按上节核对状态及需求依据。这些检查适用于所有带图片的 PRD，不依赖是否制作原型。没有实际截图或渲染证据时，如实报告限制，不声称通过。
