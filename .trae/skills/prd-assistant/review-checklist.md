# PRD 审校清单

用于评审一份 PRD 是否完整、清晰、可落地。审校前先判断需求类型（A 微调型 / B 模块级 / C 跨系统或新增复杂业务），按类型选择检查深度；输出审校结果时，优先指出高风险缺口，再给补齐建议。

## 一、先定类型与检查深度

- A 微调型：重点检查每条改动是否写清位置、内容、规则，截图是否齐全，多语言和历史数据是否遗漏；不要求完整章节，重点看改动本身说不说得清
- B 模块级：重点检查入口、字段、操作、状态、校验、异常是否闭环，主流程、异常流程、回退流程是否都有
- C 跨系统或新增复杂业务：重点检查最原始历史逻辑是否讲清、范围与排除是否明确、跨系统字段与同步关系是否对齐、校验汇总与历史数据处理是否完整
- 通用判据：研发和测试能否不追问就照着做；简单需求注水与复杂需求缺项同样算问题

## 二、通用检查项（所有类型都适用）

1. 背景是否一两句讲清现状与问题，不写空话
2. 每条改动是否写清：位置（哪个页面、哪个字段后）、内容（字段、控件、枚举、默认值、必填）、规则（展示条件、触发条件、校验、边界）
3. 截图或原型链接是否紧跟对应说明，有没有只描述不配图的改动
4. 前端文案是否带简、繁、英，文案与界面是否一致
5. 存量数据是否写清刷数、迁移、删除规则
6. 未确认内容是否标为“待确认”或“假设项”，未定项是否标【待确定】或（需评估）
7. 删除或调整的内容是否保留删除线并注明决策状态
8. 数据来源是否明确（产品库、中台配置、接口返回、上游带出），避免“同现有逻辑”“见原型”这类含糊说法
9. 术语是否全篇统一，是否混用“需求说明 / 方案 / PRD”
10. 是否明确本次不做什么（范围排除），防止范围蔓延
11. 图片是否用相对路径嵌入，没有本机绝对路径，没有「截图占位」「待补图」等占位文案；引用文件是否真实存在；图片较多时是否有截图索引
12. 语句是否通顺自然：无翻译腔，无“进行、确保、此外、值得注意的是”等套话堆砌，出声读不别扭（要求见语言表述规范.md）
13. 输入是否区分已确认事实、产品判断、假设（待确认）和开放问题，正文是否误把判断或假设写成事实
14. 追问是否只针对会改变核心流程、权限、资金/合规、数据归属、不可逆操作或关键验收的问题
15. 材料冲突是否按规则优先级处理；未解决冲突是否保留各方口径、影响和建议决策人
16. 核心需求是否有稳定 REQ/RULE/AC ID；B、C 类是否有追踪矩阵，且需求、规则、原型 `data-feature`、验收可双向定位
17. 核心功能是否有“前置条件 / 操作 / 预期结果”验收标准，并覆盖主路径和关键异常
18. 是否完成非功能适用性判断；性能、安全、可用性、兼容、审计等适用项是否有可验证口径，未确认阈值是否明确标注
19. 原型分流是否正确：仅解释截图不强制生成；需要交互、改动后效果或 PC/H5 验证时是否调用 `html-prototype`
20. 最终交付是否干净：标题、范围说明、验收标准、追踪矩阵和交付说明中是否残留被否方案的"此地无银三百两"式表述（"无 X""非 X 版""已去掉 X"等）；真实范围排除和必要事实是否保留，但被否方案解释和会话过程是否已移除（要求见 final-output-hygiene.md）

## 三、A 微调型专项检查

- 是否只写了改动相关的内容，没有注水章节（版本信息、变更日志、名词解释等非必需内容）
- 每个改动点是否独立成条，一个改动配一个截图
- 字段改动是否写全：新增字段的枚举、默认值、是否必填、展示条件
- 文案改动是否写全：原文、新文案、出现位置、多语言
- 校验改动是否写全：触发条件、报错文案
- 历史数据是否说明处理方式（刷数、迁移、不处理）

## 四、B 模块级专项检查

- 是否说明系统现状与目标，而不是只有功能描述
- 模块入口与位置是否明确
- 字段明细是否表格化，列是否覆盖：字段、控件、默认值、必填、可编辑、多语言、数据来源、备注
- 操作与交互是否写清：按钮、弹窗、确认方式、成功与失败反馈
- 状态与流转是否写清：初始状态、中间状态、终态、触发条件
- 校验与异常是否写清：前置条件、边界场景、报错文案
- 主流程、异常流程、回退流程是否都有
- 迭代优化需求是否覆盖：现状、本次改动点、不改动范围、影响范围、兼容或回归说明

## 五、C 跨系统或新增复杂业务专项检查

- 最原始的历史逻辑是否讲清：现状如何、历史上为什么这么做、本次在什么基础上改
- 本期范围说明与范围排除是否明确：涉及哪些模块、明确不做什么
- 全局基础要求是否先行定义：跨系统共用的概念、口径、索引规则
- 是否按系统分章（旧版管理端、新版管理端、用户门户、H5、APP、API、结算系统等），各章是否覆盖列表、筛选、导出、字段、交互、状态
- 跨系统字段与同步关系是否对齐：哪个系统维护、是否同步、同步后是否可编辑
- 接口口径是否明确（如涉及）：数据维度、索引口径
- 校验汇总表是否完整：校验项、触发提示
- 历史数据处理是否完整：梳理、迁移、刷数、删除及处理要求
- 是否明确哪些模块暂不考虑（备注）

## 六、按需检查项（涉及才查）

### 角色与权限边界

- 是否说明谁发起、谁审核、谁批准、谁确认、谁驳回
- 是否说明不同角色各自能看到什么、能操作什么、何时不能操作
- 是否说明页面可见范围、按钮可操作范围、数据权限或审批权限

### 数据与留痕

- 是否说明关键业务对象和核心字段
- 是否说明哪些操作需要留痕
- 是否说明历史记录、版本记录、差异追踪是否需要保留

### 异常与边界

- 是否考虑重复提交、用户中途退出、权限不足、数据缺失或状态冲突、外部依赖失败或超时
- 是否区分异常流程、异常处理规则、异常与边界场景，避免重复

### 验收可测试性

- 验收标准是否可测试，而不是口号式描述
- 是否至少覆盖主路径和关键异常路径
- 是否能让测试根据文档设计用例

## 七、常见问题清单（判断缺口的抓手）

- 只有页面原型，没有规则定义
- 只有规则说明，没有页面入口和交互细节
- 只写正常流程，不写失败和回退
- 只写最终状态，不写状态如何变化
- 只写“支持某能力”，但没有触发条件和结果
- 只写“记录日志”，但没写谁的什么操作需要记录
- 简单需求注水：小改动套大章节，正文却没有信息量
- 复杂需求缺项：跨系统需求漏写历史逻辑、校验汇总或历史数据迁移

审校时建议使用以下结构：

### 1. 总结论

- 适合直接进入评审 / 需要补充后再评审 / 暂不具备落地条件

### 2. 关键缺口

- 缺口：
  - 影响：
  - 建议补充：

### 3. 次要优化项

- 优化点：
  - 原因：
  - 建议写法：

- 建议补充内容：
- 建议补充字段或状态：
- 建议补充异常场景：
