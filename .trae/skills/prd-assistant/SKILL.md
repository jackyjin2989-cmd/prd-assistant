# PRD Assistant

## 适用范围

当用户需要以下任一结果时使用本技能：

- 从零起草正式 PRD
- 把会议纪要、聊天记录、原型说明整理成结构化 PRD
- 补全、润色已有 PRD 或草稿
- 审校 PRD 是否完整、清晰、可评审、可落地

默认输出为简体中文正式 PRD，不默认输出技术方案、接口文档或研发实现细节。

## 先分类，再决定怎么写

不是所有 PRD 都套同一结构。先判断需求属于哪一类，再决定篇幅和详细程度：

### A 微调型

- 特征：在已有页面或功能上增删字段、改文案、调校验或展示，不涉及新模块、新流程
- 写法：需求背景一两句，按模块逐条列改动点（位置、内容、规则），每条后跟截图；涉及多语言、历史数据时单列。整篇通常 1-3 KB
- 判断依据：改动落在明确页面上的明确字段、文案或按钮

### B 模块级

- 特征：新增或重构一个功能模块（页面、弹窗、流程、状态流转），主要在一个系统内完成
- 写法：版本信息 + 需求背景（现状与目标）+ 功能详细说明（按模块或页面拆分，含入口、字段、操作、状态、校验、异常）+ 多语言 + 历史数据处理；字段与规则用表格。通常 8-16 KB

### C 跨系统或新增复杂业务

- 特征：涉及旧版管理端、新版管理端、用户门户、H5、APP、API 等多个系统，或新增完整业务链路
- 写法：背景与目标（含最原始的历史逻辑）+ 本期范围说明（含范围排除）+ 全局基础要求 + 按系统分章 + 字段与规则明细 + 接口口径（如涉及）+ 校验汇总 + 历史数据处理 + 附件。篇幅允许 20-40 KB

判断不了时，按“影响哪些系统、是否新增业务链路、改动颗粒度”向用户确认，不要擅自决定。

按需模块（变更日志、文档说明/名词解释、需求范围、流程图、多语言、历史数据、校验汇总、附件等）按 [写法指南.md](写法指南.md) 的“按需模块适用条件”判断是否写，不默认全写。

## 写作前必问的背景（先问清再动笔）

- 通用：现状与痛点是什么？影响哪些系统、页面、角色？有没有原型、设计稿、截图、旧文档？PRD 是否需要在 GitLab 或 GitHub 上图文预览？有没有需要保留的最原始历史逻辑？
- A 微调型：改哪个页面的哪个字段或文案？当前取值与展示逻辑？是否涉及多语言？存量数据要不要处理？
- B 模块级：模块入口和完整流程？涉及哪些角色、状态、异常？上线后对现有流程的影响？
- C 复杂型：最原始的业务逻辑是什么（现状如何、历史上为什么这么做）？跨哪几个系统？数据归属与同步关系？接口或数据结构是否变更？存量数据如何迁移？

规则：信息不足时，把未确认内容标为“待确认”或“假设项”，不要把猜测写成事实；未定项可标【待确定】。

### 事实分层与最小追问

先将输入逐条标记为四层，标记应贯穿正文、待确认项和追踪矩阵：

- **已确认事实**：用户明确提供，或可由用户材料直接核验；正文可直接采用并注明来源。
- **产品判断**：为补全方案作出的合理设计选择；必须标注为“产品判断”，不得伪装成现状。
- **假设项**：为继续成稿暂时采用的前提；标“假设（待确认）”，并写明假设不成立时受影响的章节或规则。
- **开放问题**：当前无法安全决定、且会影响核心路径的事项；进入待确认清单。

只追问会改变核心流程、角色权限、资金或合规口径、数据归属、不可逆操作、关键验收结果的问题。一次集中提出最少问题；其余信息按已知内容继续编写，以“产品判断”“假设（待确认）”或“开放问题”显式留痕，不因非关键缺口阻塞交付。

若用户以截图或参考图片描述改动，默认由技能根据截图生成高保真带交互的 HTML 原型并自动截图，不需要用户提供原型文件。

执行前先判断交付需要：仅需解释界面时直接分析截图；需要表达改动后效果、交互路径或 PC/H5 响应式行为时，分流到 `html-prototype`。若截图文字或结构模糊，先按可辨识内容记录，不猜测；仅在用户明确授权目标网站后，通过浏览器由用户自行登录，再观察必要页面。

## 任务分流

### 1. 起草

适用于“写 PRD”“写需求文档”“根据想法输出正式需求”等场景。先做需求分类，再读取 [写法指南.md](写法指南.md) 按对应层级组织内容。

### 2. 补全或改写

适用于“补全 PRD”“润色需求”“把会议纪要整理成文档”“把草稿改成正式版”等场景。保留已确认事实，先判断需求类型，再读取 [写法指南.md](写法指南.md) 补齐缺失部分并统一术语。

### 3. 审校

适用于“评审 PRD”“检查是否完整”“看这份需求是否能给研发/测试”等场景。读取 [review-checklist.md](review-checklist.md)，先判断需求类型和检查深度，再指出关键缺口，给补齐建议。

### 4. 原型分流

满足任一条件时调用 `html-prototype`：用户要求可交互页面；需要验证 PC/H5 布局；截图无法说明状态切换、弹窗或完整流程；需要在 PRD 中提供改动后截图。只需文字评审、字段规则整理或现有截图说明时，不强制生成原型。

## 工作流程

1. 起草或补全类任务先进入规划阶段（Plan 模式）：在需求分类、业务流程、核心功能清单和关键业务规则确认前，不直接输出正式 PRD。若当前不在规划阶段，先向用户说明并请求进入规划阶段。
2. 在规划阶段先做需求分类，再按上面的提问清单收集背景；优先吸收已有材料（聊天记录、草稿、原型、页面说明、流程图、截图、PDF）。
3. 若用户提供了截图、设计稿或参考图片，先据此生成高保真带交互的 HTML 原型（还原布局与样式，实现用户描述的改动），再按 [图片嵌入与截图指南.md](图片嵌入与截图指南.md) 自动截图，作为 PRD 配图素材。
4. 输出完整计划：说明归类（A/B/C）、目标篇幅与结构大纲；计划必须包含补充完整的业务流程和详细的功能清单，细化到页面级和操作级。
5. 等待用户确认计划后，再按计划编写正式 PRD；未经确认不进入正式成稿。
6. 起草或补全时，按 [写法指南.md](写法指南.md) 对应类型的固定骨架组织，不另起结构；先写背景与现状，再写改动与规则；涉及截图时按 [图片嵌入与截图指南.md](图片嵌入与截图指南.md) 用相对路径嵌入并维护截图索引；涉及数据留痕、版本追踪、关联关系时，默认归入功能规则或附录，不单独扩成一章。
7. 同一需求里，避免把“页面展示”和“功能逻辑”重复混写。
8. 为需求、规则、原型和验收分配稳定 ID（如 REQ-01、RULE-01、AC-01）；B、C 类或用户要求可追踪时，输出追踪矩阵，至少包含需求 ID、来源/事实层级、实现章节或原型 `data-feature`、验收 ID、状态。
9. 为每项核心功能写可测试验收标准，优先使用“前置条件 / 操作 / 预期结果”，覆盖主路径和关键异常；不得使用“体验良好”“功能正常”作为唯一标准。
10. 按需判断非功能要求：只有性能与容量、可用性与恢复、安全与隐私、可访问性、兼容性、审计与留痕、国际化或可观测性会实质影响方案或验收时才写；无依据的阈值标为待确认，不自行编造。
11. 输出完成后自检：简单需求检查是否注水，复杂需求检查是否遗漏历史逻辑、字段规则、校验汇总、历史数据处理；检查追踪矩阵是否覆盖 P0/核心需求、验收是否可执行、非功能判断是否有结论；按 [图片嵌入与截图指南.md](图片嵌入与截图指南.md) 检查图片引用是否完整、无占位残留；按 [语言表述规范.md](语言表述规范.md) 出声通读，检查语句是否通顺自然、无翻译腔与套话。

原基线自检要求保留为最低门槛：

8. 输出完成后自检：简单需求检查是否注水，复杂需求检查是否遗漏历史逻辑、字段规则、校验汇总、历史数据处理；按 [图片嵌入与截图指南.md](图片嵌入与截图指南.md) 检查图片引用是否完整、无占位残留；按 [语言表述规范.md](语言表述规范.md) 出声通读，检查语句是否通顺自然、无翻译腔与套话。

## 规则优先级与冲突消解

发现材料之间或同一材料前后冲突时，不自行拼接。按以下顺序决定采用口径：

1. 用户在当前任务中的明确指令与最新确认；
2. 已确认的法规、合同、合规或安全硬约束；
3. 已批准且仍有效的业务规则、历史决策与现行产品行为；
4. 用户提供的原型、截图、会议纪要和草稿；同级材料以更新时间更晚、证据更直接者优先；
5. 产品判断和通用惯例。

低优先级不得覆盖高优先级。无法判定时保留各方说法，标明冲突位置、影响范围和建议决策人，列为开放问题；涉及资金、合规、权限或不可逆操作时必须追问确认。

## 写作核心原则

- 按系统、模块、页面组织，每条改动写清位置、内容、规则
- 背景一句话讲清现状与问题，不写套话
- 截图紧跟对应说明，有原型或设计稿时给出链接
- 前端文案必带简、繁、英三语
- 存量数据必写刷数、迁移、删除规则
- 删除或调整的内容保留删除线并标注决策状态（已确认方案、需评估、待确定、工期紧张先不改）
- 复杂需求文末汇总所有校验项与提示文案
- 篇幅服从复杂度：简单不注水，复杂不省略
- 语言表述：语句通顺自然，直接陈述、具体优先、删套话与翻译腔，要求见 [语言表述规范.md](语言表述规范.md)
- 截图与图片：用户提供截图或参考图片时，先据此生成高保真交互原型再自动截图；按 [图片嵌入与截图指南.md](图片嵌入与截图指南.md) 用相对路径嵌入，禁止绝对路径与占位文案，图片较多时维护截图索引
- 除非用户明确要求，否则不扩展成技术实现方案
