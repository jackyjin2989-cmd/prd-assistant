# PRD Assistant

## 适用范围

当用户需要以下任一结果时使用本技能：

- 从零起草正式 PRD
- 把会议纪要、聊天记录、截图、网站观察记录或原型说明整理成结构化 PRD
- 补全、润色已有 PRD 或草稿
- 审校 PRD 是否完整、清晰、可评审、可落地

默认输出为简体中文正式 PRD，不默认输出技术方案、接口文档或研发实现细节。

## 职责边界

| 任务 | 负责 Skill |
|---|---|
| 访问授权网站、处理用户接管登录、观察页面和采集证据 | `browser-observer` |
| 将多源材料整理为需求、规则、验收和待确认项 | `prd-assistant` |
| 根据需求、截图或观察记录实现并验证 HTML 原型 | `html-prototype` |

`prd-assistant` 不直接定义浏览器命令、认证、会话和页面诊断流程，也不直接实现 HTML。URL 输入先按观察目标分流；只有最终需要原型时，才在观察完成后调用 `html-prototype`。

## 输入场景判断

先判断输入类型和用户目标，再决定是否需要页面观察、PRD 或原型。详细规则见 [references/input-intake.md](references/input-intake.md)。

| 输入类型 | PRD 处理 | 页面观察 | 原型 |
|---|---|---|---|
| 纯文字描述 | 进入分类与起草 | 通常不需要 | 视复杂度和用户要求 |
| 清晰截图 / 设计稿 | 提取结构、状态和改动 | 通常不需要 | 需要页面效果或交互时调用 |
| 模糊或不完整截图 | 仅采用可辨识事实 | 有授权 URL 且缺口关键时调用 `browser-observer` | 需要时在观察后调用 |
| 网站 URL | 先明确用户要观察、写 PRD 还是出原型 | 调用 `browser-observer` | 不默认调用 |
| 会议纪要 / 聊天记录 | 提炼并做事实分层 | 不需要 | 用户要求时调用 |
| 已有 PRD 草稿 | 保留事实并按类型补齐 | 需核实现状时调用 | 视缺口和用户要求 |
| 流程图 / 架构图 | 提取流程、角色和状态 | 通常不需要 | 涉及页面时按需调用 |
| 混合输入 | 分源提取后合并 | 只观察 URL 或关键缺口 | 按最终交付决定 |

信息不足时，把未确认内容标为“待确认”或“假设项”，不要把猜测写成事实；未定项可标【待确定】。

## 需求分类

不是所有 PRD 都套同一结构。先判断需求属于哪一类，再按信息闭环程度决定内容深度；不以字节数或字数作为质量指标。

### A 微调型

- 特征：在已有页面或功能上增删字段、改文案、调校验或展示，不涉及新模块、新流程
- 写法：只覆盖背景、改动、影响和验收；按模块逐条列改动点（位置、内容、规则），每条后跟截图，按需补充多语言和历史数据处理
- 完成标准：改动边界清楚，影响可判断，验收结果可观察；不为增加篇幅补充无关章节

### B 模块级

- 特征：新增或重构一个功能模块（页面、弹窗、流程、状态流转），主要在一个系统内完成
- 写法：版本信息 + 需求背景 + 功能详细说明 + 按需模块；功能说明覆盖入口、字段、操作、状态、校验和异常，字段与规则用表格
- 完成标准：每个页面与状态形成闭环，入口、操作、状态流转、校验、异常和验收可相互对应

### C 跨系统或新增复杂业务

- 特征：涉及多个系统或端，或新增完整业务链路
- 写法：背景与目标 + 本期范围 + 全局基础要求 + 按系统分章 + 字段与规则 + 按需接口口径 + 校验汇总 + 历史数据处理 + 附件
- 完成标准：每个系统的数据归属、同步关系、异常处理和历史数据处理形成闭环，跨系统规则与验收可追踪

判断不了时，按“影响哪些系统、是否新增业务链路、改动颗粒度”向用户确认。按需模块按 [references/写法指南.md](references/写法指南.md) 的适用条件判断，不默认全写。

## 事实分层与最小追问

### 事实分层

- **已确认事实**：用户明确提供，或可由用户材料和授权观察证据直接核验；正文可直接采用并注明来源。
- **产品判断**：为补全方案作出的合理设计选择；必须标注为“产品判断”，不得伪装成现状。
- **假设项**：为继续成稿暂时采用的前提；标“假设（待确认）”，并写明不成立时受影响的章节或规则。
- **开放问题**：当前无法安全决定、且会影响核心路径的事项；进入待确认清单。

网站观察只能证明授权范围内、特定账号和状态下的现行行为；未观察到不等于不存在，现行行为也不自动等于未来需求。

### 最小追问

只追问会改变核心流程、角色权限、资金或合规口径、数据归属、不可逆操作、关键验收结果的问题。一次集中提出最少问题；其余信息按已知内容继续编写，以产品判断、假设或开放问题显式留痕。

### 写作前必问的背景

- 通用：现状与痛点是什么？影响哪些系统、页面、角色？有没有原型、设计稿、截图、旧文档或网站观察记录？PRD 是否需要图文预览？是否有必须保留的历史逻辑？
- A 微调型：改哪个页面的哪个字段或文案？当前取值与展示逻辑？存量数据是否处理？
- B 模块级：模块入口和完整流程？涉及哪些角色、状态、异常？上线后对现有流程有什么影响？
- 涉及前端文案：需要支持哪些语言？是否沿用现有多语言机制和翻译口径？用户未说明时主动确认，不默认指定语种。
- C 复杂型：原始业务逻辑是什么？跨哪些系统？数据归属与同步关系？接口或数据结构是否变更？存量数据如何迁移？

## 任务分流

### 起草

适用于写 PRD、写需求文档、根据想法输出正式需求等场景。先做需求分类和输入判断，再读取 [references/写法指南.md](references/写法指南.md) 按对应层级组织内容。

### 补全或改写

适用于补全 PRD、润色需求、把会议纪要整理成文档或把草稿改成正式版。保留已确认事实，先判断需求类型和输入来源，再补齐缺失部分并统一术语。

### 审校

适用于评审 PRD、检查完整性或判断是否足够交付研发测试。读取 [references/review-checklist.md](references/review-checklist.md)，先判断需求类型和检查深度，再指出关键缺口并给出补齐建议。

### 浏览器观察分流

满足任一条件时调用 `browser-observer`：

- 用户提供 URL，希望核实现有页面、流程或状态
- 截图模糊、裁切或缺少关键交互，且有授权网站可补充
- PRD 结论依赖真实页面的校验、权限、异常或响应式行为
- 用户要求采集页面截图、结构、状态或诊断证据

仅凭现有文字或清晰截图即可完成任务时，不为“更完整”而额外访问网站。

### 原型分流

满足任一条件时调用 `html-prototype`：

- 用户明确要求可交互页面或 HTML 原型
- 需要验证 PC/H5 布局和组件重排
- 需要表达状态切换、弹窗、完整流程或改动后效果
- 需要为 PRD 生成可验证的改动后截图

用户只要求观察网站、文字评审、字段规则整理或说明现有截图时，不强制生成原型。URL 且需要原型时，调用顺序为：`browser-observer` → `html-prototype` → `prd-assistant` 整合。

## 工作流程

1. **输入判断**：识别文字、截图、网站、纪要、草稿或混合输入，按 [references/input-intake.md](references/input-intake.md) 做事实分层和 Skill 分流。
2. **浏览器证据准备**：URL 或关键截图缺口需要核实时，调用 `browser-observer`；记录授权范围、账号角色、页面状态、证据和未验证项。
3. **需求分类**：判断 A/B/C 类型，确定信息闭环标准和结构；不设置硬性字数或字节数。
4. **规划阶段**：起草或补全类任务先确认需求分类、业务流程、核心功能清单和关键业务规则，再进入正式 PRD。
5. **背景收集**：优先吸收已有材料和观察记录，只追问影响核心结论的缺口。
6. **原型准备**：若需要原型，调用 `html-prototype` 消费需求、截图和结构化观察记录，生成高保真交互 HTML 与验证截图。
7. **输出计划**：说明归类、信息闭环要求与结构大纲，覆盖完整业务流程和页面级功能清单；篇幅仅作非约束参考。
8. **等待确认**：等待用户确认计划后，再按计划编写正式 PRD；未经确认不进入正式成稿。
9. **正式编写**：按 [references/写法指南.md](references/写法指南.md) 对应类型组织；涉及图片时按 [references/图片嵌入与截图指南.md](references/图片嵌入与截图指南.md) 使用相对路径并维护索引。
10. **追踪与验收**：为需求、规则、原型和验收分配稳定 ID；B、C 类或用户要求可追踪时输出追踪矩阵。核心功能使用“前置条件 / 操作 / 预期结果”。
11. **非功能判断**：只有性能、容量、可用性、恢复、安全、隐私、可访问性、兼容性、审计、国际化或可观测性会实质影响方案或验收时才写。
12. **自检**：检查信息闭环、事实来源、观察限制、追踪矩阵、验收可执行性、图片引用和语言表达。
13. **最终交付清理**：按 [references/final-output-hygiene.md](references/final-output-hygiene.md) 从最终采用状态重写，不保留被否方案标签和会话过程。

## 规则优先级与冲突消解

发现材料冲突时，不自行拼接。按以下顺序决定采用口径：

1. 用户在当前任务中的明确指令与最新确认
2. 已确认的法规、合同、合规或安全硬约束
3. 已批准且仍有效的业务规则、历史决策与现行产品行为
4. 用户提供的原型、截图、`browser-observer` 观察记录、会议纪要和草稿；同级材料以更新时间更晚、证据更直接者优先
5. 产品判断和通用惯例

低优先级不得覆盖高优先级。无法判定时保留各方说法，标明冲突位置、影响范围和建议决策人；涉及资金、合规、权限或不可逆操作时必须追问确认。

## 写作核心原则

- 按系统、模块、页面组织，每条改动写清位置、内容、规则
- 背景直接讲清现状与问题，不写套话
- 截图紧跟对应说明，有原型或观察证据时给出稳定引用
- 多语言根据用户需求和产品现状判断；用户未说明时主动确认语种及翻译口径，不默认三语
- 存量数据写清刷数、迁移、删除或不处理规则
- 删除或调整的内容保留删除线并标注决策状态
- 复杂需求文末汇总校验项与提示文案
- 内容深度服从信息闭环：A 类覆盖背景、改动、影响、验收；B 类确保每个页面与状态闭环；C 类确保每个系统的数据归属、同步、异常和历史数据闭环
- 语言要求见 [references/语言表述规范.md](references/语言表述规范.md)
- 图片要求见 [references/图片嵌入与截图指南.md](references/图片嵌入与截图指南.md)
- 除非用户明确要求，否则不扩展成技术实现方案

## 示例触发

- “帮我写一个充值审核流程的 PRD。”
- “把这份会议纪要整理成正式需求文档。”
- “帮我评审这份 PRD，看是否足够给研发和测试。”
- “这是当前页面的截图，把按钮从红色改成蓝色，出一份 PRD。”
- “观察这个已授权网站的注册流程，并据此写 PRD；暂时不要做原型。”
- “参考这个网站做交互原型并写 PRD。”此时先调用 `browser-observer`，再调用 `html-prototype`，最后整合 PRD。
