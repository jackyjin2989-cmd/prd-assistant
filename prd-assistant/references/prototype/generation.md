# 原型生成

交付可直接打开、可交互的自包含 HTML 原型。本模块负责原型的信息架构转译、页面实现、交互状态、响应式适配和视觉验证；是否生成原型以 `SKILL.md` 的“原型与观察分流”为唯一完整定义，本文件只描述实现方法。仅实现用户明确要求以及表达核心交互所需的最小平台、页面和状态；原型用于表达产品行为，不伪造生产能力，不携带第三方受限制资产或用户凭据。

## 输入来源

按以下优先级取用信息：

1. 用户明确需求、已确认业务规则与品牌约束；
2. 已批准的设计稿、线框图和清晰截图；
3. 页面观察输出的结构化观察记录、状态证据与脱敏截图；
4. 通用界面惯例。

不同输入场景的处理方式见 [../input-intake.md](../input-intake.md)。观察材料中已确认事实、推断、待确认项必须分开使用，未验证行为不得直接实现为确定规则。

## 观察记录转译

消费页面观察输出时，只提取原型实现所需信息：

- 页面清单、入口、导航和内容层级；
- 组件类型、字段、操作和可见文案；
- 与本次结论相关的状态（默认、加载、空、错误、禁用、弹层、校验、成功等按需选择）；
- PC/H5 的真实布局差异和未验证断点；
- 截图索引、视口、状态与证据来源。

参考网站只用于理解信息层级、布局规律、交互模式和响应式行为。不得复制受版权限制的源码、图像、字体、商标或大段文案；使用原创结构、样式、占位素材和通用图标。详细边界见 [site-reference.md](site-reference.md)。

## 原型生成流程

1. **确认输入质量**：核对需求、截图和观察记录是否覆盖核心交互；缺口标为待确认，不用猜测补齐。
2. **确定最小范围**：只选择用户明确要求和核心交互必需的平台、页面与状态；双端支持按需，不默认扩展。
3. **截图先解构**：截图是用户要求原型的主要视觉依据时，先识别产品类型、设计体系、页面骨架、组件家族、密度和视觉令牌，形成内部还原规格，再开始编码；不得跳过分析直接套通用模板。
4. **建立页面清单**：列出最小页面、主流程、必要状态与稳定功能 ID。
5. **先还原骨架再写交互**：先按截图完成全局框架、区域比例和关键组件，再补语义结构、键盘可操作性及状态逻辑；不得用“功能相近”替代“视觉一致”。
6. **状态可验证**：所有关键动作必须产生可见状态变化；避免只弹出 `alert`。
7. **设计变量统一**：从截图提取并用 CSS 变量管理颜色、间距、圆角、排版、边框和阴影；无法确认的值采用与已识别设计体系一致的最小假设。
8. **响应式适配**：对窄屏调整导航、列数、触控尺寸和固定元素，禁止仅做整体缩放。
9. **离线可用**：在无网络情况下仍可打开核心原型；若必须使用外部资源，提供降级方案。
10. **视觉闭环**：截图驱动的原型必须在目标视口渲染并与输入截图进行至少一轮人工视觉对比；能生成当前图时执行截图对比，按“骨架 → 组件 → 排版 → 装饰”顺序修正。不能渲染时必须明确说明未完成视觉验证，不得宣称高还原。
11. **验证交付**：验证核心交互可运行；控制台、溢出、多视口和完整状态覆盖按用户要求执行。截图驱动场景的目标视口视觉检查是默认步骤，其他场景仍按需执行截图对比。

## 截图驱动还原

当用户提供页面截图并要求“画原型、照着做、复刻、还原、做成可交互页面”时，截图是主视觉约束，不是普通参考图。用户需求决定功能范围，截图决定视觉语言；除非用户明确要求改版，不得擅自把截图替换成更熟悉的通用后台、卡片化首页或其他设计风格。

### 还原规格

编码前在内部记录以下内容；信息可确定时直接采用，只有影响页面骨架或关键交互且无法判断时才向用户确认：

- **界面身份**：产品类型、端类型、可能的组件体系或视觉家族，例如 Element UI 风格管理后台；只有证据充分时才命名具体体系，不能确认时描述可见特征。
- **页面骨架**：顶栏、侧栏、标签页、面包屑、筛选区、内容区、表格、分页、抽屉或弹窗的存在、顺序、宽高关系和固定方式。
- **组件规格**：按钮层级与尺寸、输入框高度、表格行高与表头、标签页形态、抽屉宽度、表单标签位置、图标位置及操作列样式。
- **视觉令牌**：主色、背景色、边框色、正文与次要文字色、字号层级、字重、行高、间距、圆角、阴影和内容密度。
- **内容与状态**：截图中可见文案、选中项、筛选值、表格数据形态、分页状态和打开中的弹层；看不到的交互不推断成确定事实。
- **目标视口**：优先使用截图像素尺寸或用户指定尺寸；截图被裁切时记录可见区域，不擅自把裁切内容当成完整页面。

### 还原优先级

1. **页面身份与骨架**：先保证一眼看上去是同一类产品和同一页面布局。
2. **几何与密度**：对齐侧栏宽度、内容边距、筛选区高度、表格列宽与行高、弹层尺寸。
3. **组件形态**：匹配标签页、表单、按钮、表格、操作列和抽屉等关键组件。
4. **排版与颜色**：匹配字号、字重、行高、主辅色、边框和背景层级。
5. **装饰细节**：最后处理图标、阴影、微小圆角和悬停反馈。

不得在骨架明显不符时先花时间润色渐变、阴影或动画。若截图是传统高密度后台，应保持其高密度、弱圆角、细边框和表格主导特征，不得默认改造成大留白、大卡片、强圆角的通用现代后台。

### 资产与组件

- 优先使用可离线交付且外观接近的通用实现；若环境已有匹配组件库，可使用其合法依赖，但不能假定库名相同就自动获得视觉一致性。
- 无法使用原设计体系时，通过 CSS 变量和局部组件样式复现可见特征，禁止把浏览器默认控件直接当成完成稿。
- 截图中的第三方商标、专有图片和受限制图标不直接复制；使用中性占位或合法替代，并说明该差异。
- 文案和数据优先沿用用户截图中可辨识、非敏感的内容；需要补数据时保持字段长度、状态分布和行数密度相近。

## PC / H5 响应式

响应式不是整体缩放，而是针对不同设备重新组织内容和交互。详细规范见 [responsive-guide.md](responsive-guide.md)。

- 只实现用户明确要求的平台；用户要求双端或核心交互确需跨端表达时，再同时实现 PC/H5。
- PC 或 H5 的具体视口、补测尺寸和断点按用户要求或目标材料确定，不预设必须覆盖两套尺寸。
- 逐项说明组件如何重排、隐藏、折叠或固定；禁止将 PC 宽表直接压缩到不可读。
- PC/H5 共享相同功能 ID 和业务状态；设备差异只改变呈现与操作方式，不擅自改变业务规则。
- 只验证已纳入范围的端和状态；未要求的双端适配或完整状态矩阵不作为默认完成条件。

## HTML 约束

- 默认交付单个 HTML，内联必要 CSS/JS。
- 使用 `header/nav/main/section/form/button` 等语义标签。
- 交互控件提供可见焦点、标签和合理的 ARIA 状态。
- 正文对比度与触控区域满足常见可访问性要求。
- 每个需求映射区域使用稳定的 `data-feature`；PRD 已使用 `REQ-001` 等需求 ID 时沿用相同值，例如 `data-feature="REQ-001"`，未编号时使用清晰、稳定的语义 ID。
- 测试所需状态可通过查询参数或明确控件稳定进入，例如 `?state=empty`。
- 不将密钥、账号、内部 URL 或真实个人数据写入前端。

## 截图对比验证

验证不是追求逐像素复制第三方作品，而是确认用户批准的目标材料与实现的一致性。区分三种情况：

- **截图驱动原型**：输入截图即本次目标材料，目标视口的人工视觉检查为默认步骤；当前环境能够渲染和截图时，应生成当前图并至少完成一轮并排比较与修正，不要求另建像素差基准。
- **自动差异截图**：只有用户明确要求、项目已有基准图或明确批准作为验收手段时执行；优先使用当前环境已有的浏览器自动化能力，不交付或长期维护独立 Selenium 截图脚本 SOP。
- **普通原型或基准回归**：非截图驱动场景按验收需要人工检查；项目已有基准图且纳入验收范围时再做基准回归，没有基准图时不强制创建。

1. 固定浏览器版本、视口、缩放、字体和页面状态。
2. 分别截取基准图与当前图，文件名包含页面、视口和状态。
3. 同时检查像素差异与语义差异：布局、层级、文案、状态、操作可达性。
4. 先修复结构性问题，再调整间距、字号和颜色。
5. 设置项目自己的阈值；超过阈值时输出差异图并人工复核。
6. PC 与 H5 分开设基准，动态时间、随机数据和动画应固定或遮罩。

详细方法见 [visual-validation.md](visual-validation.md)。

## 交付清单

- 原型 HTML（可直接打开运行）；
- 如用户要求，提供脱敏后的本地参考图和差异图；
- 截图驱动原型提供简要还原说明：目标视口、已匹配的骨架与组件、仍存在的合法资产或输入缺口差异；
- 按需验证记录：视口、路径、状态、交互结果、控制台错误、差异结论；
- 已知限制、未验证状态和待确认项。

## 完成标准

- 用户要求的平台与核心主流程可完成；
- 纳入范围的页面无明显遮挡或不可点击控件；
- 核心操作可达；
- 用户要求的控制台、溢出、多视口和状态检查已完成；截图驱动原型已在目标视口完成至少一轮视觉检查，其他原型的截图对比仍按需执行；
- 观察记录中的未验证项没有被伪装成已确认行为；
- 产物不包含敏感信息、公司专用词或第三方受限制内容。
