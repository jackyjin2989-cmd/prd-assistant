# PRD 审校清单

先判断需求类型，再检查核心产品信息是否足以评审和验收。不要用模板章节数量衡量质量，也不要因缺少技术方案、运营手册或原型而判定 PRD 不完整。

## 一、内容边界

默认内容边界以 `SKILL.md` 的“默认内容边界”为唯一完整定义。审校时检查：

- 是否围绕本次核心功能和改动，没有无关扩写。
- 用户未明确要求、且不直接决定产品行为的越界内容是否已删除。
- 产品可见异常是否只说明触发条件、反馈和用户下一步，没有推导内部实现。

## 二、通用检查

1. 背景是否简洁说明现状、问题和目标。
2. 每条改动是否写清位置、条件、行为、规则和结果。
3. 角色、页面、字段、操作、状态是否只覆盖实际涉及的部分。
4. 枚举、默认值、必填、展示条件和校验文案是否明确。
5. 用户可见异常是否有明确反馈和可继续路径。
6. 存量数据是否只在受影响时说明处理规则。
7. 内部是否区分现状与问题，且最终稿没有暴露分析分类或判断过程。
8. 材料冲突是否按最新用户确认和权威来源处理。
9. 同一规则是否只定义一次，没有跨章节重复或口径漂移。
10. 术语是否统一，语句是否直接、自然、无套话。
11. 核心分歧是否已集中追问并暂停定稿；非关键待确认是否未进入确定性验收。

## 三、按类型检查

### A 微调型

- 是否只保留背景、改动和直接影响。
- 文案改动是否给出位置和最终文案。
- 字段改动是否写清取值、默认值、必填、展示和校验。
- 是否避免版本信息、名词解释、流程图等注水内容。

### B 模块级

- 功能入口和适用角色是否明确。
- 页面、字段、操作、关键状态和业务规则是否闭环。
- 用户操作前后的可见结果是否明确。
- 是否只写产品层异常，没有默认补技术恢复机制。

### C 跨产品复杂业务

- 核心业务流程、共同角色和状态口径是否明确。
- 各产品端的入口、展示、操作和结果是否互相一致。
- 跨端规则是否集中定义，没有重复复制。
- 是否避免自动扩展成系统架构、接口或同步时序文档。

## 四、观察、原型与图片

- 材料足够时，是否直接完成 PRD，没有为“更完整”额外观察页面。
- 只有用户明确要求或关键产品事实必须核实时，才执行页面观察（见 [browser/observation.md](browser/observation.md)）。
- 只有用户明确要求原型/交互验证，或经确认文字无法表达核心方案时，才生成原型（见 [prototype/generation.md](prototype/generation.md)）。
- 是否避免因存在页面、弹窗、截图或响应式场景就自动做原型。
- 截图驱动原型是否先识别界面身份、页面骨架、组件形态、密度和视觉令牌，未擅自改成通用模板。
- 是否区分目标页面、裁切区域和浏览器外壳等非目标内容，并按截图尺寸或用户指定尺寸确定目标视口。
- 是否按 [prototype/visual-validation.md](prototype/visual-validation.md) 完成目标视口验证，记录结论为“通过 / 受限 / 未完成”以及剩余差异。
- 未完成视觉验证时，是否避免使用“高还原”“已复刻”或“视觉验收通过”等确定性表述。
- 图片仅在能澄清改动时使用；路径为相对路径且文件存在。

## 五、编辑残留与最终交付

- 最终稿是否删除删除线、草稿标记、占位文字、批注式说明、会话过程及“XX问题已判断/已解决”等分析过程字样。
- 标题、范围和交付说明是否只描述最终采用方案。
- 被否方案是否未以“无 X”“非 X 版”“已去掉 X”等方式重新出现。
- 真实且必要的范围排除是否简洁保留，没有附带讨论过程。
- 是否没有重复章节、重复规则、矛盾结论或断裂链接。
- PRD 正文中是否不含需求/规则/验收编号（如 REQ-01、RULE-01），也没有追踪矩阵章节。
- PRD 与原型是否为独立文件，原型未嵌入 PRD 正文。
- 交付物包含原型时，原型主要模块、页签、弹窗的截图是否嵌入 PRD 对应章节正文后，无裂图和占位。

## 六、审校输出

建议按以下顺序输出：

1. **结论**：可评审 / 补充后可评审 / 核心方案待确认。
2. **关键缺口**：只列影响核心功能的问题，说明影响与建议。
3. **重复与矛盾**：指出位置并给统一口径。
4. **可直接替换的文本**：用户需要时提供。

不要把默认不要求的技术、发布、运营或原型内容列为缺口。
