# PRD 写法指南

先判断需求属于 A 微调型、B 模块级还是 C 跨产品复杂业务，再选择足以说明核心功能与改动的最小结构。模板是裁剪工具，不是必填目录。`SKILL.md` 的"简单需求必须简单写"优先于本文件的任何建议结构。目标形态和常见写坏方式见 [示例.md](示例.md)。

## 一、通用写法

每份 PRD 优先回答：

1. 改什么：涉及的页面、模块、角色或用户路径。
2. 如何表现：入口、字段、操作、状态、业务规则和用户可见反馈。
3. 还有什么未定：只保留影响核心方案的待确认项。

背景与目标只在 B/C 类需要铺垫时写；A 类一句话或省略。

动笔前按 [边界扫描清单.md](边界扫描清单.md) 内部过一遍本次改动类型对应的小节；扫出的问题只有影响本次改动才写进 PRD。

### 默认内容边界

以 `SKILL.md` 的"默认内容边界"为唯一完整定义。本指南只补充写法：产品层异常说明"何时发生、用户看到什么、可以怎么继续"，不设计内部恢复机制。

### 规则优先用表格

字段、展示规则、状态流转、触发条件与文案，优先用表格承载，一行一条可执行规则；散文只用于交代背景和串联逻辑。字段表常用列：字段、控件、取值、默认值、必填、可编辑、展示条件、校验文案；没有的信息不为填满列而推测。

### 表格的下限（防止过度表格化）

"优先用表格"是上限不是下限。表格只承载**有真实口径的行**：

- 该写进表格：枚举、取值来源、校验规则、状态流转、空态与条件展示、权限与可见性。
- 不该单列成行：一眼能看出的展示字段（日期、数值、单位、金额换算、标题、标签），以及只有 2–3 行且都无规则的清单 —— 用一句话带过。
- 图表下方的数值（日期 / 数值 / 简单换算）不逐字段拆表，合并成一句，例如「图下方展示选中区间末日的日期、单位净值与区间收益（区间末净值 ÷ 区间首净值 − 1，后端计算）」。
- 同一意义上的「取值来源 + 展示逻辑」两列都有内容才算一行；只有「—」的行不要建。

自检问句：**这一行删掉，研发会不会做错？** 不会就别单列。典型反例：把页首信息卡的「基金名称 / 币种标签 / ISIN 代码 / 更新日期」做成 4 行 3 列表，其中三行的取值来源和逻辑都是「—」。

### 存量数据处理的写法

先判断本次改动是否影响已有业务数据；不影响就不写。影响时按三种方式选择并写清，同一需求不同字段可用不同方式，逐项写，不写"存量数据保持不变"一句带过：

| 方式 | 适用 | 必须写清 |
|---|---|---|
| 兼容展示 | 旧数据不改，新页面兼容显示 | 旧数据在列表、详情、导出中显示什么（如「—」）；是否参与筛选和统计 |
| 一次性刷数 | 旧数据按新规则统一初始化 | 刷数范围和取值规则；刷数前是否留档；刷不出来的数据怎么处理 |
| 新老划断 | 上线后新数据用新规则，存量不动 | 划断时点；在途单据按新旧哪套规则；两类数据并存时各处展示口径 |

### 权限的写法

按用户要求写权限点的改造：权限点名称、控制的入口和操作范围、无权限时的页面表现（不展示入口 / 置灰 / 提示无权限）。不输出角色权限矩阵，不推导各角色应配置哪些权限。

### 按需内容（默认都不写，满足条件才写）

| 内容 | 何时写 |
|---|---|
| 验收标准 | 仅用户明确要求时 |
| 范围排除（本期不做） | 仅用户明确要求，或不写会导致读者误解边界时；一句话列出，不解释原因 |
| 版本信息、变更日志 | 用户要求或多人长期维护 |
| 名词解释 | 专有名词多且影响理解 |
| 流程图 | 多角色、多状态且文字不易说明；统一用 Mermaid（flowchart 或 stateDiagram），不用 ASCII 图或纯文字步骤伪装的流程图 |
| 图片 | 用户要求，或能明显降低页面改动歧义 |
| 原型 | 以 `SKILL.md` 的"原型分流"为准，不因写 PRD 顺带制作 |
| 多语言 | 用户明确要求或已有产品机制要求 |
| 校验汇总 | 校验分散且数量较多 |
| 非功能要求 | 用户明确要求，或属于必须写入产品的约束 |
| 成功判定 | 需求本身包含增长、效率、转化等目标；写基线、目标值和观察周期，不扩展为埋点方案 |

### 不输出内容

以下内容不得出现在 PRD 正文中：

- 需求、规则、验收的编号标识（如 REQ-01、RULE-01、AC-01）和追踪矩阵
- 事实分层标签（已确认事实、产品判断、假设项等分类说明）
- 被否方案、删除线保留、草稿过程和会话残留
- 总结段、"本 PRD 覆盖了……"等自证句

## 二、A 微调型

适合字段、文案、展示条件、校验等局部改动。**硬性上限：正文通常半页以内，只有两部分。**完整示例见 [示例.md](示例.md)。

1. **需求背景**：一句话说明为什么改；不言自明时省略。
2. **改动点**：按页面或位置逐条说明。

每条改动写：位置、条件（何时展示/可编辑）、内容（增/改/删什么）、规则（取值、默认值、必填、校验）、结果（操作后看到什么）。哪项没有就不写哪项，不为格式完整凑内容。

影响既有功能或存量数据时加一条影响说明；没有就不写。不写目标、验收、范围排除、总结。不默认配图。

## 三、B 模块级

适合新增或重构一个页面、弹窗、模块或业务流程。

### 建议结构

1. **背景与目标**（一段以内，编号短句列出现状与本期要做的事）
2. **本期范围说明**（改动涉及两个以上页面/模块时用范围表：模块 × 本期新增或调整内容，一行一个模块）
3. **功能详细说明**（按页面或模块分节展开）
4. **业务规则与关键状态**（规则少时并入详细说明，不单开章节）
5. **存量数据处理**（按需，写法见通用节）
6. **待确认项**（按需）

### 功能详细说明

按页面、模块或用户路径组织，覆盖实际涉及的内容：入口与适用角色、页面结构和字段、用户操作与结果、关键状态及流转条件、展示与校验规则、用户可见的失败反馈与下一步。

带流转的状态用状态表写全：状态、含义、可执行操作、流转条件；异常分支（失败、驳回、取消）单独说明停在哪个状态、展示什么。

## 四、C 跨产品复杂业务

适合多个产品端、角色或完整业务链路。重点是统一产品口径与跨端体验，不自动扩展为系统设计。

### 建议结构

1. **背景与目标**
2. **本期范围说明**（范围表：系统/模块 × 本期关注点；可加"重点说明"列出两三条全局口径）
3. **全局业务规则**（共同业务对象、核心概念、计算规则和状态口径集中定义；主流程用 Mermaid）
4. **按系统或产品端分模块说明**（每端一章，只写该端的入口、展示、操作和结果）
5. **存量数据处理**（按需，写法见通用节）
6. **待确认项**（按需）

### 写法要点

- 先在"全局业务规则"定义共同对象、枚举和计算口径，再分端引用，各端章节不重复展开。
- 跨端联动写明方向：哪个端的什么操作，引起哪个端的什么变化。
- 写清各端展示什么、谁能操作、操作后业务状态如何变化。
- 仅在用户要求技术方案时补接口、数据结构、同步时序。

## 五、事实与冲突

写作时内部区分已确认事实、产品判断、假设和开放问题，只用于判断哪些能直接写入、哪些标待确认，不把这份分类写进正文。材料冲突的优先级以 `SKILL.md` 的"冲突处理"为唯一完整定义。

## 六、表达与图片

- 使用直接陈述句，避免套话和重复结论。
- 枚举、状态和错误文案能明确时写全，不写"等"。
- 图片用相对路径，紧邻所说明的改动；图片规则见 [图片嵌入与截图指南.md](图片嵌入与截图指南.md)。
- 语言细则见 [语言表述规范.md](语言表述规范.md)。
