# PRD 写法指南

先判断需求属于 A 微调型、B 模块级还是 C 跨产品复杂业务，再选择足以说明核心功能与改动的最小结构。模板是裁剪工具，不是必填目录。

## 一、通用写法

每份 PRD 优先回答：

1. 为什么改：现状、问题和目标。
2. 改什么：涉及的页面、模块、角色或用户路径。
3. 如何表现：入口、字段、操作、状态、业务规则和用户可见反馈。
4. 如何验收：前置条件、操作、预期结果。
5. 还有什么未定：只保留影响核心方案的待确认项。

### 默认内容边界

默认内容边界以 `SKILL.md` 的“默认内容边界”为唯一完整定义。本指南只补充写法：产品层异常说明“何时发生、用户看到什么、可以怎么继续”，不设计内部恢复机制。

### 按需内容

| 内容 | 何时写 |
|---|---|
| 版本信息、变更日志 | 用户要求或多人长期维护 |
| 名词解释 | 专有名词多且影响理解 |
| 范围说明 | 影响面大或存在容易误解的产品范围 |
| 流程图 | 多角色、多状态且文字不易说明 |
| 图片或原型 | 用户要求，或能明显降低页面改动歧义 |
| 多语言 | 用户明确要求或已有产品机制要求 |
| 存量数据处理 | 本次功能会影响已有业务数据 |
| 校验汇总 | 校验分散且数量较多 |
| 追踪矩阵 | 用户要求、跨团队协作或规则确实难以定位 |
| 非功能要求 | 用户明确要求，或属于必须写入产品验收的约束 |

需要追踪时，按 `REQ-001`、`REQ-002` 递增编号；原型对应区域使用相同值，例如 `data-feature="REQ-001"`。不需要追踪时不强制为每条需求编号。

## 二、A 微调型

适合字段、文案、展示条件、校验等局部改动。

### 建议结构

1. **需求背景**：一两句说明现状与问题。
2. **改动点**：按页面或位置逐条说明。
3. **影响说明**：仅写本次改动直接影响的既有功能或存量数据。
4. **验收标准**：可以紧跟各改动点，不必另起大章。

### 改动点写法

- 位置：在哪个页面、区域或字段附近。
- 条件：何时展示、可编辑或可操作。
- 内容：新增、修改或删除什么。
- 规则：取值、默认值、必填、校验、状态变化。
- 结果：用户操作后看到什么。

不默认配图；已有截图能澄清位置时直接引用。最终稿不使用删除线保留被淘汰方案。

## 三、B 模块级

适合新增或重构一个页面、弹窗、模块或业务流程。

### 建议结构

1. **背景与目标**
2. **功能范围**
3. **功能详细说明**
4. **业务规则与关键状态**
5. **存量数据处理**（按需）
6. **验收标准**
7. **待确认项**（按需）

### 功能详细说明

按页面、模块或用户路径组织，覆盖实际涉及的内容：

- 入口与适用角色
- 页面结构和字段
- 用户操作与结果
- 关键状态及流转条件
- 展示、编辑、提交和校验规则
- 用户可见的失败反馈与下一步

字段较多时使用表格：字段、控件、取值、默认值、必填、可编辑、展示条件、校验文案。没有的信息不要为填满列而推测。

## 四、C 跨产品复杂业务

适合多个产品端、角色或完整业务链路。重点是统一产品口径与跨端体验，不自动扩展为系统设计。

### 建议结构

1. **背景与目标**
2. **本期功能范围**
3. **核心业务流程**
4. **按产品端或角色说明功能**
5. **跨端业务规则与状态**
6. **存量数据处理**（按需）
7. **验收标准**
8. **待确认项**（按需）

### 写法要点

- 先定义共同业务对象、角色和状态，再分端说明用户行为。
- 同一规则只在一处完整定义，其他章节引用，避免复制。
- 写清各端展示什么、谁能操作、操作后业务状态如何变化。
- 仅在用户要求技术方案时补接口、数据结构、同步时序等内容。
- 验收覆盖完整业务主链路和关键产品异常，不默认覆盖基础设施异常。

## 五、成功判定（按需）

需求本身包含增长、效率、转化、质量或风险目标时，补充可判断的成功条件。普通文案、字段和局部页面调整不要求量化指标。

- 有明确目标值时写基线、目标值和观察周期。
- 无法量化时写定性成功条件，例如"用户可在 3 步内完成 X 操作"。
- 功能验收通过不等于业务目标达成；两者分开写。

不默认扩展为埋点方案、数据分析或监控方案。

## 六、事实与冲突

- **已确认事实**：用户材料或授权证据可直接支持。
- **产品判断**：为形成方案作出的选择，必要时标注。
- **假设（待确认）**：暂时采用且会影响方案的前提。
- **开放问题**：当前不能决定的核心问题。

材料冲突时采用用户当前任务的最新明确确认；仍无法判断且影响核心功能时，列出冲突和影响并追问。无关冲突不写进最终 PRD。

## 七、验收写法

核心功能使用：

| 前置条件 | 操作 | 预期结果 |
|---|---|---|
| 用户处于可操作状态 | 执行具体动作 | 页面、业务状态或可见结果明确变化 |

验收标准描述最终采用的产品行为，不描述被否方案，也不写开发过程、发布方式或内部监控。

## 八、表达与图片

- 使用直接陈述句，避免套话和重复结论。
- 枚举、状态和错误文案能明确时写全，不写“等”。
- 图片用相对路径，紧邻所说明的改动；图片规则见 [图片嵌入与截图指南.md](图片嵌入与截图指南.md)。
- 用户未要求原型时，不因页面类需求自动制作原型或截图。
- 语言细则见 [语言表述规范.md](语言表述规范.md)。
