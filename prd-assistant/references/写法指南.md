# PRD 写法指南（分层写法）

本指南按需求类型分层。先按 SKILL.md 的需求分类（A 微调型 / B 模块级 / C 跨系统或新增复杂业务）确定深度，再按对应层级的固定骨架组织。每个类型都有固定骨架（见各节首张表），输出时按骨架顺序组织，不另起结构；骨架内标“必填”的模块不可省略，标“按需”的模块按实际情况取舍。不设硬性字数或字节数，通常篇幅只能作为非约束参考。判断标准是信息是否闭环，以及“研发和测试能不能直接照着做”，不是“章节齐不齐”或“篇幅够不够”。

## 一、通用要素与按需模块适用条件

每份需求文档都围绕以下要素展开，按类型取舍：

- 现状与问题：用一两句话讲清为什么做，不写空话
- 改动点：按系统、模块、页面逐条列出，每条写清位置、内容、规则
- 截图或原型：每条改动后紧跟对应截图；图片用相对路径嵌入（`![图片简述](相对路径/文件名.png)`），禁止本机绝对路径与占位文案，规范见图片嵌入与截图指南.md
- 多语言：涉及前端文案时，根据用户需求和产品现状判断；用户已明确语言范围时按要求输出，未说明时主动确认所需语种及是否沿用现有翻译口径，不默认指定语种
- 历史数据处理：凡影响存量数据，写清刷数、迁移、删除规则
- 决策标注：删除或调整的内容保留删除线，未定项标【待确定】或（需评估）
- 范围排除：明确本次不做什么，防止范围蔓延

### 按需模块适用条件（动笔前判断，不默认全写）

| 模块 | 何时写 | 何时不写 |
| --- | --- | --- |
| 版本信息 | B、C 必写；A 不写 | 用户未要求的 A 类 |
| 变更日志 | 多轮迭代、多人协作 | 一次成稿 |
| 文档说明/名词解释 | 跨系统、缩写术语多（旧版管理端、新版管理端、用户门户、业务中台等） | 术语自明 |
| 用户调研/竞品分析 | 需求本身有调研或竞品依据 | 内部规则调整类 |
| 需求范围 | 影响面大、易蔓延，或跨系统 | A 类一句话归入备注 |
| 流程图（Mermaid） | 多步流程、状态流转 | 单页字段级改动 |
| 多语言 | 用户明确要求，或现有产品存在多语言机制；涉及前端文案但用户未说明时先确认 | 用户确认仅需单一语言，或无用户可见文案 |
| 历史数据处理 | 影响存量数据 | 纯新增、无存量 |
| 校验汇总 | 校验项多且分散各节 | 校验少、就地写清即可 |
| 备注/范围排除 | 有明确不做的事 | 无歧义 |
| 验收标准 | 所有类型均写；A 可紧跟改动点 | 无可观察结果的纯说明性文档 |
| 追踪矩阵 | B、C，或多人协作、跨系统、用户要求可追踪 | 单一 A 类且改动与验收一一对应 |
| 非功能要求 | 性能、安全、兼容、可用性等会影响方案或验收 | 无实际影响或无依据 |

### 增量质量模块

- **事实分层表**：按“已确认事实 / 产品判断 / 假设（待确认） / 开放问题”记录来源、结论和影响章节；正文中不得把后两类写成事实。
- **验收标准**：为核心需求分配 AC ID，使用“前置条件 / 操作 / 预期结果”，至少覆盖主路径与关键异常。
- **规则冲突记录**：记录冲突材料、各自来源、适用范围、采用口径和待决策人；优先级遵循 SKILL.md。
- **追踪矩阵**：建议列为“需求 ID、需求摘要、来源/事实层级、规则 ID、实现章节或原型 data-feature、验收 ID、状态”。
- **非功能判断**：逐项判断性能与容量、可用性与恢复、安全与隐私、可访问性、兼容性、审计与留痕、国际化、可观测性；只展开“适用”项，无来源的数值阈值标待确认。

## 二、A 微调型写法

信息密度要求：只覆盖背景、改动、影响和验收；确保改动边界明确、影响可判断、验收可观察，不为增加篇幅补充无关章节。

固定骨架（输出时按此顺序组织，不另起结构）：

| 顺序 | 模块 | 要求 | 说明 |
| --- | --- | --- | --- |
| 1 | 需求背景 | 必填 | 一两句讲清现状与问题 |
| 2 | 改动点（按模块或页面分节） | 必填 | 每条写清位置、内容、规则，紧跟截图 |
| 3 | 多语言 | 按需 | 见按需模块适用条件 |
| 4 | 历史数据 | 按需 | 见按需模块适用条件 |
| 5 | 备注或范围说明 | 按需 | 有需要说明的排除项时 |

写法要点：

- 每条改动独立成条，一个改动配一个截图，不合并
- 每条改动写清位置（哪个页面、哪个字段后）、内容（字段、控件、枚举、默认值、必填）、规则（展示条件、校验、边界）
- 校验必须配精确提示文案，开发不应自行发明
- 能用一句话说完的不展开成段落
- 不写版本信息、变更日志、名词解释等重章节，除非用户明确要求

示例（蒸馏自历史需求）：

- 需求：账户增加投资者类型标签
  - 客户账户管理基本信息增加“投资者类型”字段，下拉列表：机构专业投资者、企业/法团专业投资者、个人专业投资者、非专业投资者
  - 销售 Account 的搜索范围按所选投资者类型过滤；账户全称后增加投资者类型英文标签
  - 每处配截图；历史数据待运营提供刷数
- 需求：赎回页增加“待复核份额”
  - 定义：交易审批中 Pending Approval 状态的全部赎回份额合计，大于 0 时才显示
  - 可赎回份额与全部赎回按钮需减去待复核份额；excel 下单同样校验，不足则按赎回份额不足处理
  - 若用户确认需要繁体中文与英文，则补充：待復核份額 / Reviewing Shares；若未说明语言范围，先确认后再补充

## 三、B 模块级写法

信息密度要求：每个页面与状态形成闭环，入口、字段、操作、状态流转、校验、异常和验收可相互对应。

固定骨架（输出时按此顺序组织，不另起结构）：

| 顺序 | 模块 | 要求 | 说明 |
| --- | --- | --- | --- |
| 1 | 版本信息 | 必填 | 版本号、创建日期、审核人、期望上线时间 |
| 2 | 变更日志 | 按需 | 多轮迭代或多人维护时：时间、版本号、变更人、主要变更内容 |
| 3 | 文档说明/名词解释 | 按需 | 系统名、角色、业务术语缩写对照表 |
| 4 | 需求背景 | 必填 | 系统现状 + 目标 + 原型或设计稿链接；有调研或竞品依据时补一句关键结论 |
| 5 | 需求范围 | 按需 | 影响面大时写，明确本期范围与“暂不包含” |
| 6 | 功能详细说明 | 必填 | 按模块或页面分节，先交互图/原型再展开；多步流程附 Mermaid 流程图；含入口、功能说明表（序号/模块/功能/功能详细说明/交互图）、字段明细表、操作交互、状态流转、校验异常、截图 |
| 7 | 多语言 | 按需 | 前端文案汇总表 |
| 8 | 历史数据处理 | 按需 | 刷数、迁移、删除规则 |
| 9 | 校验汇总 | 按需 | 校验项多且分散各节时文末汇总：校验顺序、校验项、触发提示 |
| 10 | 备注或范围说明 | 按需 | 不改动范围、影响范围、兼容/回归说明 |
| 11 | 附件 | 按需 | 原型、excel、设计稿、接口文档、调研截图与页面路由参考 |
| 12 | 验收标准 | 必填 | 核心功能逐项给出 AC ID、前置条件、操作、预期结果 |
| 13 | 追踪矩阵 | 必填 | 关联需求、事实层级、规则、原型与验收 |
| 14 | 非功能要求 | 按需 | 先判断适用性，再写可验证口径 |

写法要点：

- 先写主流程，再写异常流程和回退流程
- 字段规格逐字段展开：类型、必填、可选值/校验规则、错误提示、默认值、联动依赖；禁止“有姓名、性别、日期三个字段”一句话带过
- 下拉/枚举穷举全部选项，不写“等”
- 联动写清触发字段 + 触发值 → 展示/隐藏哪些字段
- 异常覆盖：空态、边界值、超时、网络中断、服务端拒绝
- 字段、状态、枚举能表格化就表格化
- 明确数据来源：取自产品库、中台配置、接口返回、上游页面带出等
- 迭代优化类需求补充：现状、本次改动点、不改动范围、影响范围、兼容/回归说明，按内容归位到对应章节，不单独成章

## 四、C 跨系统或新增复杂业务写法

信息密度要求：每个系统的数据归属、同步关系、异常处理和历史数据处理形成闭环，跨系统规则、数据变化与验收结果可追踪。

固定骨架（输出时按此顺序组织，不另起结构）：

| 顺序 | 模块 | 要求 | 说明 |
| --- | --- | --- | --- |
| 1 | 背景与目标 | 必填 | 最原始历史逻辑 + 现状 + 目标 + 设计或原型链接 |
| 2 | 本期范围说明 | 必填 | 新增/调整范围表、重点说明与关注点、明确“暂不包含” |
| 3 | 全局基础要求 | 必填 | 跨系统共用概念、口径、索引规则先行 |
| 4 | 按系统分章 | 必填 | 旧版管理端、新版管理端、用户门户、H5、APP、API、结算系统等；每章开头先写本章改造目标，再写列表筛选导出表、字段表、交互状态表、接口口径；各章自包含，不跨章引用 |
| 5 | 多语言 | 按需 | 前端文案汇总表 |
| 6 | 校验汇总 | 按需 | 校验项多时必写，含触发提示 |
| 7 | 历史数据处理 | 按需 | 影响存量数据时写，梳理、迁移、刷数、删除及处理要求；可单章也可归入对应模块 |
| 8 | 备注 | 按需 | 范围排除、暂不考虑的模块 |
| 9 | 附件 | 按需 | 原型、excel、设计稿、接口文档链接、调研截图与页面路由参考 |
| 10 | 验收标准 | 必填 | 覆盖跨系统主链路、关键异常和数据一致性 |
| 11 | 追踪矩阵 | 必填 | 关联需求、事实层级、规则、系统章节、原型与验收 |
| 12 | 非功能要求 | 按需 | 先判断适用性，再写可验证口径 |

写法要点：

- 先讲清最原始的历史逻辑，再写改动，读者才能理解在什么基础上改
- 同一规则只在一处展开，其他章节引用，避免重复
- 跨系统字段清单用大表对齐（例如：字段分类、字段名称、是否同步、是否可编辑、是否本次变更、备注）
- 明确数据归属与同步关系（哪个系统维护、向哪个系统同步、同步后是否可编辑）
- 字段规格逐字段展开、枚举穷举、校验配文案、异常覆盖，要求同 B 型

## 五、文笔与说法规范

语句通顺与去 AI 腔的完整要求见 [语言表述规范.md](语言表述规范.md)，本节只列文档结构类规范：

- 用直接陈述句描述行为：新增字段【发行方】，位于【产品名称】下方；点击确认后，状态变更为已结算
- 能枚举就枚举：下拉选项、状态、类型全部列出，不写“等”
- 规则写成条件句：何时展示、何时可点、何时置灰、何时报错，报错文案写全
- 数据来源写清：取自哪里，避免“同现有逻辑”“见原型”这类含糊说法
- 删除线保留原决策痕迹：~~原逻辑~~（已确认方案）
- 未确定项显式标注：【待确定】、需评估是否必须、工期紧张先不改
- 多语言按用户确认的语种范围汇总成表格，列名使用对应语言名称；不默认固定为简、繁、Eng
- 涉及金额、流程、跨端时，标注注意回归测试的相关链路
- 术语全篇统一，不混用“需求说明 / 方案 / PRD”

## 六、常用表格式样

- 字段明细表：字段、控件、默认值、是否必填、是否可编辑、是否多语言、数据来源、备注
- 字段规格表（表单页逐字段）：字段、类型、必填、可选值/校验规则、错误提示、默认值、联动依赖
- 功能说明表：序号、模块、功能、功能详细说明、交互图
- 变更日志表：时间、版本号、变更人、主要变更内容
- 改动调整表：涉及调整字段、调整、描述或备注（常用于列表筛选、字段、状态调整）
- 多语言表：文案位置、文案标识、用户确认的各语种列、翻译来源或状态
- 校验汇总表：校验顺序、校验项、触发提示
- 跨系统同步表：字段分类、字段名称、是否同步、是否可编辑、是否本次变更、备注

## 七、图片与截图规范

- 嵌入格式：`![图片简述](相对路径/文件名.png)`，路径相对 PRD 所在目录
- 禁止：本机绝对路径、截图占位、待补图等纯文字占位
- 放置：每个主要模块或关键弹窗，在对应章节正文后嵌入；弹窗先打开再截取，不截空白态
- 命名：序号-模块名.png
- 索引：图片较多时，PRD 末尾维护截图索引列表
- Git 平台：相对路径是 GitLab / GitHub 渲染图片的前提；引用路径与磁盘文件一一对应，不得裂图
- 原型生成与自动截图：用户提供截图或参考图片时，由技能生成高保真带交互的 HTML 原型并自动截图，流程见图片嵌入与截图指南.md
