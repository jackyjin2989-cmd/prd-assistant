# 图片嵌入与截图指南

本指南约束 PRD 中图片的选择、命名、脱敏、引用与排布，包括原型截图的嵌入。HTML 原型的实现与交互由 [prototype/generation.md](prototype/generation.md) 定义，视觉验证由 [prototype/visual-validation.md](prototype/visual-validation.md) 定义。本指南不维护独立自动化 SOP。

## 图片选择

- 优先使用用户提供、项目自有或已获授权的截图、设计稿与原型图。
- 图片应直接支持相邻需求说明；无信息增量的装饰图、重复图和与当前版本不一致的旧图不纳入 PRD。
- 截图模糊时只采用可辨识内容；无法辨识的文案、数据和规则标为待确认，不放大猜测。
- 需要制作或验证 HTML 原型时按 [prototype/generation.md](prototype/generation.md) 执行，不要在 PRD 写作流程中默认生成原型或截图。

## 原型截图嵌入

交付物包含 HTML 原型时，对原型截图并嵌入 PRD，让读者不打开原型也能看到页面形态。执行前先按 [prototype/visual-validation.md](prototype/visual-validation.md) 的"截图能力判定"确认环境可截图；判定不可截图时跳过嵌入，在 PRD 中用一句话注明"原型截图受环境限制未提供，请直接打开原型文件查看"，不尝试配置环境。

- 对原型的主要模块、页签、弹窗截图，在 PRD 对应章节正文后嵌入，一个改动对应一个可截图的呈现。
- 用户提供原页面截图时，原型截图展示改动后的效果；需要对比时输出改动前后对照。
- 弹窗须先打开再截取目标元素，不截空白态。
- **插图时记录进入该状态的方式**（如 `?state=modal`，或「点击手动重跑 → 展开基金公司下拉」），写进交付说明或截图索引。原型改版后要重拍时，照着记录就能复现同一状态，不必重新猜当时截的是哪一态。
- 截图命名遵循本指南命名规则；截图较多时在 PRD 末尾维护截图索引。
- 静态截图只作辅助说明，交互原型仍以独立 HTML 文件交付，PRD 中不嵌入可运行原型代码。

## 命名

- 文件名应稳定、可读并能识别页面或状态，建议使用 `序号-模块-状态.png`，例如 `01-订单列表-空状态.png`。
- 同一文档内保持统一命名风格；避免无语义名称、临时名称和重复文件名。
- 尽量不使用空格及特殊字符；已有文件名无法调整时，在 Markdown 路径中正确进行 URL 编码。
- 插入或删除截图后，**按文档出现顺序整体重编号**，并同步更新全部引用；交付前校验「引用数 = 实际文件数、无未引用文件」（`scripts/scan_prd.py` 可兜底查出编号断号与未引用图片）。

## 脱敏

- 嵌入前遮蔽或替换姓名、手机号、邮箱、证件号、账号、组织信息、订单号、内部地址及其他敏感数据。
- 不保留密码、验证码、Cookie、令牌、登录态或可用于还原真实用户身份的信息。
- 脱敏后仍应保留理解需求所需的布局、字段类型和状态关系。

## 相对路径与存在性

- 使用 Markdown 图片语法：`![图片简述](相对路径/文件名.png)`。
- 路径必须相对 PRD 所在目录，禁止本机绝对路径、`file://` 地址和仓库外路径。
- 图片替代文本应简洁描述页面、模块或状态，不能留空。
- 每个引用路径必须对应实际存在的文件，文件名大小写与扩展名保持一致，避免裂图。
- 最终文档不得残留“截图占位”“待补图”等纯文字占位。

## 图片排布

- 每张截图必须紧跟对应描述或对应小标题，让读者无需跨段查找其含义。
- 禁止把各模块截图统一堆到章节末尾或文档末尾。
- 一段说明涉及多张状态图时，分别放在各自状态说明之后，并用明确的替代文本区分。
- 图片与正文的先后关系应在 GitHub、GitLab 等常见 Markdown 预览中保持清晰。

## 多图横排

同一页面、同一链路或同一组状态的相似截图（多签页、多步骤、多状态）**横排合并**，不要一张一张竖着堆。竖排会让文档被图片拉得很长，评审时要不停滚动。

用内联 HTML 表格横排，图注写在图下：

```html
<table>
<tr>
<td align="center" valign="top"><img src="images/01-xxx.png" alt="图注" width="250"><br>图注</td>
<td align="center" valign="top"><img src="images/02-xxx.png" alt="图注" width="250"><br>图注</td>
</tr>
</table>
```

单图居中：`<p align="center"><img src="images/01-xxx.png" alt="图注" width="260"></p>`。

宽度按每行张数取，保证在常见文档宽度下不溢出、仍可辨读：

| 每行张数 | 单张宽度 |
|---|---|
| 1 张 | 260 |
| 2 张 | 250 |
| 3 张 | 230 |
| 4 张 | 180 |

- **优先凑对照组**：正反两态（如「有晨星 / 未采购晨星」）、同一链路的前后步骤并排，比分散单张更省段落也更好读。
- 手机端页面截图建议 3–4 张一行，PC 后台页面截图建议 2 张一行（PC 图信息密度高，缩太小看不清）。
- 横排依赖 Markdown 渲染器支持内联 HTML（GitLab、GitHub、VS Code 预览均支持）。交付时点明这一点；若目标环境不支持 HTML，改用纯 Markdown 竖排并说明。
- 交付前把横排块渲染出来看一遍（可用无头浏览器在文档宽度下截图核对），确认无溢出、图注完整。

## 交付前检查

- 图片来源合规且内容与当前需求一致。
- 文件命名清晰、统一，无临时文件名。
- 敏感信息已脱敏。
- 所有引用均为仓库内相对路径，且目标文件存在。
- 每张截图紧跟对应描述或小标题，没有统一堆放到章节末尾。
- 无图片占位、无裂图、无本机绝对路径。

### 截图内容必须与正文口径一致

截图和正文是同一份需求的两面，对不上就是缺陷。逐项核对：

- **正文写了某个条件或状态的效果，配图必须是该状态下的实拍**，不能拿默认态顶替。例：正文写「未采购晨星时不展示评级图标」，配图里就不该出现「晨星评级 ★★★★」。
- **开关类状态要截到对应状态**：晨星有/无、有权限/无权限、空态/有数据，正文提到哪个就截哪个。
- **改了文案、样式或状态逻辑后，先列受影响截图清单再重拍**，不要留着旧图（字号、间距、隐藏逻辑一变，旧图就可能与正文矛盾）。
- 交付前抽一遍：逐张读图，反问「这张图能不能支持它旁边那句话」。对不上就重截，或把正文改成实际呈现的样子。
