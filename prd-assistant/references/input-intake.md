# 输入场景与分流判断

用户的输入形式多种多样。先判断输入类型和用户目标，再分别决定是否需要页面观察、是否需要 HTML 原型，避免将 URL 输入等同于原型任务。

## 输入场景总览

| 输入类型 | 处理路径 | 是否调用 `browser-observer` | 是否调用 `html-prototype` |
|---|---|---|---|
| 纯文字描述 | 进入需求分类与起草 | 否 | 视页面复杂度和用户要求 |
| 清晰截图 / 设计稿 | 解析结构、状态和改动 | 否 | 需要页面效果或交互时调用 |
| 模糊或不完整截图 | 记录可辨识内容；若有授权网站则补充观察 | 有 URL 且缺口影响结论时调用 | 需要原型时，在观察后调用 |
| 网站 URL | 先明确观察目标和授权范围 | 是 | 仅在用户要原型或页面方案时调用 |
| 会议纪要 / 聊天记录 | 提炼需求并做事实分层 | 否 | 用户要求或涉及关键页面时调用 |
| 已有 PRD 草稿 | 保留事实并按类型补齐 | 需核实现行页面时调用 | 视缺口和用户要求 |
| 流程图 / 架构图 | 提取流程、角色和状态 | 否 | 涉及页面且需要可视化时调用 |
| 混合输入 | 按来源分别提取后合并 | 仅处理 URL 或需核实部分 | 按最终交付目标决定 |

## 场景一：纯文字描述

**信号**：用户只用文字描述需求，没有附件或链接。

**处理**：
1. 直接做需求分类（A/B/C）
2. 按“写作前必问的背景”收集关键信息
3. 信息不足处标假设或待确认
4. 进入起草或补全流程

**原型判断**：
- A 类默认不出，用户要求时再出
- B 类涉及关键页面且文字不足以表达交互时建议出
- C 类只为核心流程和高风险状态出，不为所有章节机械配图

## 场景二：截图或设计稿

**信号**：用户提供一张或多张界面截图、线框图、设计稿。

**处理**：
1. 解析页面结构、布局、控件、文案和可见状态
2. 判断文字是否可辨识、布局是否完整、关键交互是否缺失
3. 清晰度足够时直接作为需求或原型输入
4. 信息不足且用户提供了授权网站时，调用 `browser-observer` 补充必要页面和状态
5. 没有可访问网站时，只记录可确认内容，其余标为待确认
6. 需要原型时，再调用 `html-prototype` 并将截图或观察记录作为输入

截图看不清的内容不猜测；只显示部分页面时不补造完整页面；多图需区分不同页面与同一页面的不同状态。

## 场景三：网站 URL

**信号**：用户给出网址，希望参考、核实现状、了解流程或据此制作方案。

**处理**：
1. 先明确用户目标：只观察、写 PRD、制作原型，或三者组合
2. 调用 `browser-observer` 确认授权范围、登录边界、可操作范围、脱敏要求和目标设备
3. 获取结构化观察记录，包括页面、状态、交互、响应式、证据和未验证项
4. 需要 PRD 时，由 `prd-assistant` 将观察事实转为需求、规则、验收和待确认项
5. 需要原型时，再调用 `html-prototype` 消费观察记录和脱敏截图

URL 输入不代表必须生成原型。用户只要求核实现状或评审页面时，到观察记录或 PRD 交付即可。

浏览器操作、认证、会话、快照、诊断和证据格式见 `browser-observer` 的 [SKILL.md](../../browser-observer/SKILL.md)。网站观察结果的原创转译和版权边界见 `html-prototype` 的 [site-reference.md](../../html-prototype/references/site-reference.md)。

## 场景四：会议纪要或聊天记录

**信号**：用户贴出会议纪要、聊天记录、语音转文字稿等。

**处理**：
1. 通读全文并提取需求要点
2. 逐条区分已确认事实、产品判断、假设和开放问题
3. 梳理业务流程、角色、页面和状态
4. 判断需求类型（A/B/C）
5. 按对应类型组织成结构化 PRD
6. 将不同意见区分为已达成共识和待决策，开放问题集中列入待确认清单

口语化表达应转成正式产品语言但不改变原意；玩笑和题外话不写入 PRD。

## 场景五：已有 PRD 草稿

**信号**：用户要求补全、润色、审校或将草稿改成正式版。

**处理**：
1. 通读现有文档并判断需求类型
2. 评估已有章节与关键缺口
3. 保留已确认事实，不擅自改动用户明确写定的内容
4. 按类型骨架补齐缺项并统一术语
5. 只有需要核实现行页面时才调用 `browser-observer`
6. 只有需要补充页面方案或交互证据时才调用 `html-prototype`
7. 按审校清单自检

## 场景六：流程图或架构图

**信号**：用户提供流程图、状态图、架构图、思维导图等。

**处理**：
1. 提取业务流程、角色、状态流转
2. 识别涉及的系统和模块
3. 判断需求类型
4. 页面级细节缺失时标假设或待确认
5. 涉及界面且用户需要可交互表达时，调用 `html-prototype`

## 场景七：混合输入

**信号**：用户同时提供文字、截图、链接、草稿等多种材料。

**处理**：
1. 各材料先按对应路径独立提取
2. 仅将 URL 和必须核实的页面缺口交给 `browser-observer`
3. 将截图、设计稿和观察记录按证据来源标记
4. 合并到 PRD 时处理冲突并保留来源
5. 只有最终交付包含原型时才调用 `html-prototype`

## 输入优先级

多个输入源不一致时，按以下原则处理：

1. 用户在当前任务中的最新明确确认
2. 已确认的法规、合同、合规或安全硬约束
3. 已批准且仍有效的业务规则和历史决策
4. 在授权范围内通过 `browser-observer` 观察到的现行产品行为
5. 用户提供的设计稿、截图、正式 PRD、纪要和草稿；同级材料优先采用更新、更直接的证据
6. 产品判断和通用惯例

低优先级不得覆盖高优先级。现行页面行为只能证明“当前如此”，不能自动证明“未来需求应保持如此”；无法判定时保留冲突、影响和建议决策人。
