# 输入场景与分流判断

先判断用户要什么交付，再决定是否需要观察页面或制作原型。默认使用用户已提供的材料完成 PRD；观察和原型都是按需能力，不是写 PRD 的前置步骤。

## 场景总览

| 输入 | 默认处理 | 观察页面 | 制作原型 |
|---|---|---|---|
| 纯文字、纪要、聊天记录 | 提炼核心功能与改动 | 不需要 | 不需要 |
| 清晰截图或设计稿 | 提取可见结构、文案、状态 | 不需要 | 用户明确要求时 |
| 模糊或不完整截图 | 使用可确认内容，其余标待确认 | 关键结论必须核实且有授权 URL 时 | 用户明确要求时 |
| 网站 URL | 先确认用户是否要求访问或核实现状 | 用户要求，或关键事实必须核实时 | 用户明确要求时 |
| 已有 PRD | 修复矛盾、重复和编辑残留 | 仅为核实关键现状 | 用户明确要求时 |
| 流程图、架构图 | 提取业务角色、流程和状态 | 不需要 | 用户明确要求时 |
| 混合材料 | 分来源提取并合并 | 仅处理必要 URL 或关键缺口 | 按明确交付要求 |

表中“观察页面”“制作原型”列是场景化摘要；完整触发条件以 `SKILL.md` 的“原型与观察分流”为唯一完整定义。

## 文字、纪要和聊天记录

1. 内部只区分现状与问题，再提取目标、角色、功能、规则和待确认项。
2. 判断 A/B/C 需求类型。
3. 将口语整理为产品语言，不改变原意。
4. 会改变核心方案或验收的分歧集中追问并暂停定稿；其余使用最小假设并标待确认，不进入确定性验收。

不因缺少截图而自动要求原型，也不为验证普通描述访问网站。

## 截图和设计稿

1. 只采用可辨识的页面结构、控件、文案和状态。
2. 区分不同页面和同一页面的不同状态。
3. 截图足以支持改动说明时直接写 PRD。
4. 关键交互无法从截图确认时，优先标待确认；仅在用户提供授权页面且结论必须核实时观察。
5. 用户明确要求交互原型或改动后页面时，再按 [prototype/generation.md](prototype/generation.md) 制作原型。

## 网站 URL

URL 不自动等于观察任务，也不自动等于原型任务。

- 用户只提供 URL 作为背景，但核心需求已经明确：直接写 PRD，不访问。
- 用户要求核实现状、采集证据或说明当前流程：按 [browser/observation.md](browser/observation.md) 观察相关页面和状态。
- 用户要求参考网站制作原型：先观察必要部分，再按 [prototype/generation.md](prototype/generation.md) 制作原型。
- 用户未授权访问或不需要核实：不访问；无法确认的信息标为待确认，若影响核心方案或验收则按“事实与冲突”集中追问。

## 已有 PRD

1. 识别有效事实、核心改动和用户确认。
2. 删除重复规则、过期草稿、删除线、占位文案、会话说明和被否方案残留。
3. 统一矛盾口径；影响核心方案且无法判断时再追问。
4. 按 A/B/C 的最小结构补齐产品功能和验收。
5. 不因旧文档包含技术、发布或运营章节就默认保留；按用户要求和产品必要性裁剪。

## 事实与冲突

材料冲突的完整优先级以 `SKILL.md` 的“冲突处理”为唯一完整定义。本文件只补充输入处理要求：

- 当前产品行为只能证明现状，不能自动成为未来需求。
- 会改变核心方案或验收的冲突集中追问并暂停定稿。
- 非关键缺口可标待确认继续处理，但不得进入确定性验收。
