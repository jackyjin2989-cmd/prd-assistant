# 输入场景与分流判断

先判断用户要什么交付，再决定是否需要制作原型。默认使用用户已提供的材料完成 PRD；原型是按需能力，不是写 PRD 的前置步骤。本 Skill 不访问网站，页面现状一律以用户提供的截图和描述为准。

## 场景总览

| 输入 | 默认处理 | 制作原型 |
|---|---|---|
| 纯文字、纪要、聊天记录 | 提炼核心功能与改动 | 不需要 |
| 清晰截图或设计稿 | 提取可见结构、文案、状态 | 用户明确要求时 |
| 模糊或不完整截图 | 使用可确认内容，其余标待确认 | 用户明确要求时 |
| 网站 URL | 不访问；请用户提供截图 | 用户明确要求时 |
| 已有 PRD | 修复矛盾、重复和编辑残留 | 用户明确要求时 |
| 流程图、架构图 | 提取业务角色、流程和状态 | 用户明确要求时 |
| 混合材料 | 分来源提取并合并 | 按明确交付要求 |

原型的完整触发条件以 `SKILL.md` 的"原型分流"为唯一完整定义。

## 文字、纪要和聊天记录

1. 提取目标、角色、功能、规则和待确认项。
2. 判断 A/B/C 需求类型。
3. 将口语整理为产品语言，不改变原意。
4. 会改变核心方案的分歧集中追问并暂停定稿；其余使用最小假设并标待确认。

不因缺少截图而要求原型，也不为验证普通描述要求用户补材料。

## 截图和设计稿

1. 只采用可辨识的页面结构、控件、文案和状态。
2. 区分不同页面和同一页面的不同状态。
3. 截图足以支持改动说明时直接写 PRD。
4. 关键交互无法从截图确认时标待确认；确有必要时请用户补充对应状态的截图。
5. 用户明确要求交互原型或改动后页面时，再按 [prototype/generation.md](prototype/generation.md) 制作原型。
6. "截图驱动原型"指用户明确要求页面骨架、组件形态、密度或视觉风格以所提供截图为主要依据；截图只用于说明内容、字段或业务状态时，不进入该流程。
7. 开始还原前判断材料性质：项目自有、用户原创或已获授权的材料可作为直接视觉目标；第三方页面或来源不明的材料只抽象布局、组件和视觉特征，不逐像素复制品牌资产或专有组合。来源不明且用户要求高保真复刻时，先确认授权边界。
8. 截图被裁切、缩放或混入聊天界面、浏览器外壳时，先划定目标页面区域；只有缺失部分会改变骨架或关键交互时才追问。

## 网站 URL

不访问 URL。处理方式：

- 用户只提供 URL 作为背景，核心需求已明确：直接写 PRD。
- 需要页面现状才能写清改动：请用户提供相关页面和状态的截图。
- 用户无法提供截图：按现有材料处理，无法确认的信息标待确认；影响核心方案时集中追问。

## 已有 PRD

1. 识别有效事实、核心改动和用户确认。
2. 删除重复规则、过期草稿、删除线、占位文案和被否方案残留。
3. 统一矛盾口径；影响核心方案且无法判断时再追问。
4. 按 A/B/C 的最小结构补齐核心内容；旧文档比新标准冗长时同步精简。
5. 不因旧文档包含技术、发布或运营章节就默认保留。

## 事实与冲突

材料冲突的完整优先级以 `SKILL.md` 的"冲突处理"为唯一完整定义。补充两点：

- 当前产品行为只能证明现状，不能自动成为未来需求。
- 会改变核心方案的冲突集中追问并暂停定稿；非关键缺口标待确认继续处理。
