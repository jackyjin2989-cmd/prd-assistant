# 输入场景与分流判断

用户的输入形式多种多样。先判断输入类型，再走对应的处理路径，避免信息遗漏或错误猜测。

## 输入场景总览

| 输入类型 | 典型信号 | 处理路径 | 是否调用 html-prototype |
|---------|---------|---------|----------------------|
| 纯文字描述 | "帮我写一个 XX 功能的 PRD" | 直接进入需求分类与起草 | 视复杂度而定 |
| 截图 / 设计稿 | 用户附一张或多张界面图 | 先解析截图结构，再按改动需求生成原型 | 是 |
| 网站 URL | "参考 XX 网站的 YY 页面" | 授权后用浏览器观察页面架构 | 是 |
| 会议纪要 / 聊天记录 | 用户贴一段文字记录 | 提炼需求要点，标注事实层级 | 否（除非用户要求出原型） |
| 已有 PRD 草稿 | "补全这份 PRD" / "润色一下" | 保留已确认内容，按类型补齐缺项 | 视情况 |
| 流程图 / 思维导图 | 一张流程图或架构图 | 提取业务逻辑与状态流转 | 否（除非涉及页面） |
| 混合输入 | 文字 + 截图 + 链接 | 按优先级融合，各自走对应路径 | 视情况 |

## 场景一：纯文字描述

**信号**：用户只用文字描述需求，没有附件或链接。

**处理**：
1. 直接做需求分类（A/B/C）
2. 按"写作前必问的背景"收集关键信息
3. 信息不足处标假设或待确认
4. 进入起草/补全流程

**是否出原型**：
- A 类：默认不出，用户要求才出
- B 类：关键页面建议出原型
- C 类：核心流程页面建议出原型

## 场景二：截图或设计稿

**信号**：用户提供一张或多张界面截图、线框图、设计稿。

**处理**：
1. 先解析截图：页面结构、布局方式、控件类型、文案、状态
2. 判断清晰度：文字是否可辨识、布局是否完整
3. 清晰度足够 → 直接据此生成 HTML 原型
4. 清晰度不足 → 先按可辨识内容记录，标注"从截图识别，可能有偏差"；如用户提供了目标网站，走"网站 URL"场景的浏览器观察流程补充
5. 原型完成后自动截图，作为 PRD 配图

**注意事项**：
- 截图中看不清的内容不猜测，标【待确认】
- 截图只显示部分页面时，只还原可见部分，不脑补完整页面
- 多图时注意是否为同一页面的不同状态，还是不同页面

## 场景三：网站 URL

**信号**：用户给出一个网址，说"参考这个页面"或"照着这个做"。

**处理**：
1. 确认授权范围：可以访问哪些页面、哪些功能可以点击、是否需要登录
2. 确认安全边界：是否包含真实数据、是否需要脱敏
3. 需要登录时：由用户自行完成登录，不索取凭据
4. 用浏览器观察页面：
   - 打开目标页面，等待加载完成
   - 截取完整页面截图（PC 和 H5 视口各一张）
   - 记录页面结构：导航、主要区域、控件、交互方式
   - 点击关键按钮/链接，观察状态变化和跳转
   - 记录响应式行为：缩放窗口看布局如何变化
5. 基于观察结果生成 HTML 原型
6. 原型截图对比验证

浏览器观察的详细操作方法见 `html-prototype` 的 [browser-observation.md](../../html-prototype/references/browser-observation.md)。

**安全红线**：
- 只访问用户明确授权的页面
- 不记录、不输出密码、Cookie、令牌、个人信息
- 截图前遮蔽真实姓名、头像、邮箱、手机号、订单号等
- 不复制受版权限制的源码、图像、字体、商标
- 使用原创结构和样式，参考布局和交互模式，不逐像素抄袭

## 场景四：会议纪要或聊天记录

**信号**：用户贴了一段会议纪要、聊天记录、语音转文字稿等。

**处理**：
1. 通读全文，提取需求要点
2. 逐条做事实分层：已确认 / 产品判断 / 假设 / 开放问题
3. 梳理业务流程、角色、页面、状态
4. 判断需求类型（A/B/C）
5. 按对应类型组织成结构化 PRD
6. 开放问题集中列在待确认清单

**注意事项**：
- 口语化表达要转成正式产品语言，但不改变原意
- 多人讨论中的不同意见要区分：已达成共识 / 待决策
- 聊天中的玩笑话、题外话不写入 PRD
- 有歧义的地方标【待确认】，不要自行定夺

## 场景五：已有 PRD 草稿

**信号**：用户说"补全这份 PRD""润色一下""把草稿改成正式版"。

**处理**：
1. 通读现有文档，判断需求类型
2. 评估完整性：哪些章节已有、哪些缺失
3. 保留已确认事实，不擅自改动用户明确写定的内容
4. 按类型骨架补齐缺项
5. 统一术语和表述风格
6. 走审校清单自检

## 场景六：流程图或架构图

**信号**：用户提供流程图、状态图、架构图、思维导图等。

**处理**：
1. 提取业务流程、角色、状态流转
2. 识别涉及的系统和模块
3. 判断需求类型
4. 页面级细节缺失时标假设或待确认
5. 如涉及界面，可调用原型 Skill 出页面原型

## 场景七：混合输入

**信号**：用户同时提供多种材料（文字 + 截图 + 链接 + 草稿）。

**处理**：
1. 按优先级融合信息：
   - 用户明确确认的内容 > 截图/网站观察 > 草稿 > 聊天记录
   - 有冲突时按"规则优先级与冲突消解"处理
2. 各材料分别走对应路径提取信息
3. 统一整合到 PRD 结构中
4. 追踪矩阵中标注每条需求的来源

## 输入优先级

当多个输入源信息不一致时，按以下优先级采纳：

1. 用户在当前任务中的明确确认
2. 授权网站上观察到的现行产品行为
3. 用户提供的设计稿和截图（更新者优先）
4. 已有的正式 PRD / 文档
5. 会议纪要、聊天记录
6. 产品判断和通用惯例

低优先级不得覆盖高优先级。无法判定时保留各方说法，标明冲突位置和影响范围。
